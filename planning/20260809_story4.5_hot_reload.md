# Hot reload: what a DAP `restart` does on a mounted device, and what it cannot do

Date: 2026-08-09
HEAD: 878c9bc (micropython 49502103e3, micropython-lib 84aaf65)
Story: EPIC-4 / STORY-4.5

## The shape that landed

`mpremote debug --loop <target> <module>:<method>` over a mounted source
directory. One process, one DAP session, one handshake, many runs of the target:

- The launcher (`launcher/mpy_launch_debugpy.py`, vendored byte-for-byte into
  `mpremote/mpy_launch_debugpy.py`) calls `debugpy.enable_restart()` *before*
  `wait_for_client()`, because that is where `initialize` is answered and
  `supportsRestartRequest` has to be true by then. A session not launched in
  loop mode does not advertise it and refuses a `restart` request outright, with
  a message saying why - a client's restart button must not silently do nothing.
- Each iteration re-arms tracing (`debug_this_thread()`) and imports the target
  inside the loop body. The loop's own code is deliberately outside the traced
  region: a restart handled while the loop waited would otherwise unwind the
  loop itself.
- `_handle_restart` sets a flag, releases a target parked at a breakpoint
  (clearing any pending step so it does not stop again on its way out), answers
  the request, and sends `continued` so the client's UI does not stay stopped on
  a frame that is about to cease to exist. The unwind happens where the trace
  function returns to, not in the handler.
- The unwind itself is a `RestartRequest` raised from the trace function, which
  is why `py/profile.c` had to be fixed first
  (`20260809_settrace_raise_unwind.md`) and why it derives from `BaseException`.
- Between runs, `wait_for_restart()` pumps DAP messages so a request does not
  sit unread in the socket, and returns False if the client leaves - a session
  with nobody to restart for ends rather than spinning.

## Eviction: a snapshot diff, not a path rule

The ticket sketched "the target module plus modules whose `__file__` sits under
the project source root(s)". What landed instead is the set of everything added
to `sys.modules` since a baseline taken just before the first target import:

```python
baseline_modules = set(sys.modules)   # after wait_for_client(), before run 1
...
for name in list(sys.modules):
    if name not in baseline:
        del sys.modules[name]
```

Three reasons this is the better rule, all of them about what cannot go wrong:

- **The debugger can never be in the set.** Every module debugpy needs was
  imported before the baseline was taken, so "never evict `debugpy.*`" is a
  property of the construction rather than a blacklist that a future import
  could outgrow. Evicting the running debugger is self-destruction, and a
  blacklist is exactly the kind of thing that is right until someone adds a
  module.
- **It needs no `__file__`.** MicroPython does set `__file__` on a module
  imported from a file, but on a mounted session it reads as the *device* path
  (`/remote/app.py`), so a host-side "is it under the source root" test would
  need the path mapping applied before it could answer - the same mapping the
  client needs, for a decision the device has to make alone. Frozen modules have
  no `__file__` at all.
- **A changed submodule comes back with its parent.** The classic hot-reload
  hole is reloading `app` while `helper` stays cached, so the new `app` calls
  the old `helper`. Anything the target imported is in the diff, at any depth.

Measured: `evicted == ["app", "helper"]` for a target that imports one
submodule, with nothing else in the set.

## Run boundaries are visible to the client, not just to stdout

A re-run announces itself as
`MPDBG-RESTART {"iteration": N, "evicted": [...]}` and deliberately *not* as
another `MPDBG-READY`: the endpoint has not changed, and a caller that re-parsed
one would think a second session had started.

That marker, and the `MPDBG-DEGRADED` warning next to it, go to the client's
debug console (a DAP `output` event, category `console`) as well as to stdout,
through `debugpy.console()`. Neither channel reaches everyone on its own: a
mounted serial session's filesystem pump discards everything the device prints,
so on the transport this story is *about*, stdout is a dead end; and a caller
reading stdout may have no DAP client of its own. The text is identical on both,
so there is one format to parse.

What is still never sent in loop mode is `terminated`. A client that sees it
tears the session down, which is the opposite of what loop mode is for.

## Two restart requests before the first completes

Both are answered, and each request restarts. Beyond that the division into runs
is not pinned: two requests arriving together may be drained into one unwind, or
the second may be read during the next run and unwind that one too.
`_raise_if_restarting` clears the flag as it raises, so the exception is the
whole signal - a second request during an unwind is a fresh restart rather than a
repeat of the one in flight.

The test asserts the invariant rather than an iteration count: both requests
answered, session still answering afterwards, and a complete run of the edited
sources eventually happening. An iteration count would be asserting a scheduling
accident.

## What is verified, and how

`tests/test_s4_5_hot_reload.py`, four tests over a live session: a unix firmware
process as the device on a real pty, `mpremote resume debug --loop --source ...`
as its own subprocess, a fake VS Code client on the reported endpoint.

The fixtures make the criteria checkable by construction. `app.py` and
`helper.py` exist only under the mounted host directory and are not on the
device's `MICROPYPATH`, so new code running at all proves the mount served the
edited file - there is no copy on the device that an upload could have refreshed.
The edit changes `helper.bump` from `i` to `i * 10` and adds a `stamp()` that
does not exist in v1, so:

- run 1 stops at `app.py`'s tail with `total == 3` and never reaches the
  v2-only line;
- run 2, after one `restart` and with no breakpoint re-sent, stops on the
  v2-only line inside the reloaded submodule and reads `total == 30`.

Breakpoints are set once before `configurationDone` and never re-sent, since
that they still bind is one of the things under test. Exactly one `MPDBG-READY`
for the whole session, and an unchanged device pid, is what rules out a reset or
a relaunch. Line numbers come from marker comments in both versions of each
fixture, so editing a fixture cannot silently move a breakpoint onto the wrong
line.

Deliberately not asserted: how many times a breakpoint inside the loop body is
hit. MicroPython emits one more `line` event for a loop body than it has
executions (`20260809_settrace_line_event_fidelity.md`), and a test that pinned
the count would cement a VM artifact as expected behaviour.

The teardown assertions live in the one test that detaches its client first,
because that is the sequence with a responsive device to unmount: the device's
`wait_for_restart` sees the channel gone, the target ends, and the device is back
at a raw-REPL prompt when the signal arrives. Signalling mpremote while the
client still holds a target parked in the restart wait is the case
`test_s4_3_mount_attach.py` already covers, and its documented outcome is that
only a power cycle clears the mount.

## Harness: consuming messages in arrival order

`tests/helpers.py` gains `take_msg(server, event=/response=/match=)`, which walks
a per-server cursor forward and consumes every message exactly once, in arrival
order. A session that stops several times per run needs it: `wait_for_msg`
requires the awaited message to be the *most recent* one, so anything that lands
while the test is looking elsewhere is missed, and the same event cannot be
awaited twice without a `clear_messages()` in between.

This is not the order-insensitive matching that the risk register records as
settled-as-don't. That attempt scanned the whole list for a match, so a stale
match from an earlier request satisfied the wait early. A cursor cannot do that
for any message it has already passed, which is what makes "the next stop after
this continue" expressible at all. `wait_for_msg` is unchanged and still used
where a test awaits one response with nothing else in flight; `take_msg` is
opt-in.

The first blocker attributed to loop mode was this, not a product defect: a
smoke script cleared the message list at the top of each iteration, and run 2's
`stopped` event arrived while it was polling device stdout for `MPDBG-RESTART`.
The device log disproved the channel-closed hypothesis it had been read as -
`wait_for_continue` never reported a lost connection.

## Findings not fixed

- **The DAP `pause` request does nothing.** `PdbAdapter.paused` and
  `DebugSession.paused` are written by `_handle_pause`, `pause()` and
  `_handle_restart`, and read by no stop decision anywhere. So a `pause` request
  is answered with success and the target never stops. A fix is about four lines
  (stop at the next `line` event, reason `pause`) plus a harness with a
  long-running target to drive it, which no current test has; it is a session
  story's work, not this one's.
- MicroPython's spurious loop-body `line` event, and the `return`-event line
  attribution behind the `should_stop` gate: see
  `20260809_settrace_line_event_fidelity.md`.

## Observed flake

One run in three of the new test's `start()` failed with
`mounting '...' failed (timeout waiting for first EOF reception)` before the
handshake; the same run's retry and every run since succeeded, and
`test_s4_3_mount_attach.py`'s two live sessions (identical setup, no `--loop`)
pass consistently. The readiness gate before mpremote is launched is a fixed
0.3 s sleep in both files, which is the suspect. It is left alone rather than
papered over with a retry: the deterministic alternative - opening the pty slave
from the test to probe for a REPL - risks the device seeing EOF on its own stdin
when that fd closes, which would trade an occasional visible failure for a
race that kills the device.
