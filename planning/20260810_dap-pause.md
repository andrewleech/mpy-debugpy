# The `pause` request, and the state that made it look implemented

- Date: 2026-08-10
- Top repo HEAD: `cfef4d6ed3`
- `micropython`: `4eaafbc5bc` (`mpy-debugpy`)
- `micropython-lib`: `1eb7c82bfd` (`mpy-debugpy`), before this change

STORY-6.6. The defect was found on 2026-08-09 while closing STORY-4.5 and was
filed rather than fixed, on the grounds that it needed a harness nothing in the
suite could provide. This is that story.

## What it did

`_handle_pause` set `DebugSession.paused` and `PdbAdapter.paused`, called
`PdbAdapter.pause()`, and answered the request with success. `should_stop`,
the only stop decision, read neither field. So the client was told the request
had been accepted, VS Code moved its UI to the stopped state, and the program
kept running.

The UI being wrong is not the whole cost. A stopped client asks for
`stackTrace`, then `scopes`, then `variables`, and all three are answered from
`self.current_frame` - whatever frame the target happened to be in when the
last trace event fired. The user is shown a frame the program has already left,
with values that were true at some unspecified moment, and nothing in the
exchange says so.

## Why no test caught it

Every scenario in the host suite drives a target that stops on its own at a
breakpoint. A pause is only meaningful against a target that was going to keep
running, and there was no such target to drive. That is the whole reason the
risk row said "fix with a session story, not in passing": the fix is small and
the harness is the work.

`src/spinner.py` is that target. It advances a module global once every 5 ms up
to a bound, so it runs for about two seconds and then ends on its own - a test
that fails to pause it fails rather than hangs.

## The state that hid it

Two `paused` fields and a `stepping` field, between them written eleven times
and read once:

| field | writes | reads |
|-------|--------|-------|
| `DebugSession.paused` | 6 | 0 |
| `DebugSession.stepping` | 6 | 1 (the stop-reason ladder) |
| `PdbAdapter.paused` | 3 | 0 |

Read a handler in isolation and it looks like a mechanism: `_handle_pause` sets
a flag, and somewhere else must act on it. Nothing did. The ladder's
`STOP_REASON_PAUSE` branch was unreachable - a stop was a breakpoint if
`hit_breakpoint`, else a step if `stepping`, else a pause, and with pause never
producing a stop the last branch could not be taken.

So the fix is not only the four lines that consume the flag. The reason now
comes from the adapter, which is what made the decision: `should_stop` returns
True for a breakpoint, a consumed pause, or a landed step, and records which in
`hit_breakpoint` / `hit_pause`. Those three are exhaustive, which is what lets
`DebugSession.paused` and `DebugSession.stepping` be deleted rather than left
write-only for the next reader to mistake for state.

## Two decisions in the four lines

**Only `line` events.** The same distinction `should_stop`'s breakpoint check
already makes: `call` reports the `def` line before the body has run and
`return` reports a frame that has already produced its value. Neither is a
place a user asked to stop at.

**A pending step dies with the pause.** A pause is a user interrupt; a step
that outlived it would fire later at a point nobody asked for.

## The case that only shows up when you try it

A `pause` sent while the target is already stopped at a breakpoint. The client
sending it already believes the target is stopped - VS Code will not, but the
protocol allows it and a script might. `wait_for_continue` drains the socket
while stopped, so the request is handled there and sets the flag; the next
`continue` would then stop the program one line into its next run, for a reason
nobody asked for.

`wait_for_continue` clears the flag on the way out, which is the point at which
"a pause arrived while we were stopped" is exactly the set of pauses to drop.
Both halves are mutation-checked: removing the `should_stop` consumption makes
the first scenario fail, removing this clear makes the second one fail, and
each fails only its own.

## What is not fixed

A pause can only land where Python is running, because the trace hook is the
only thing that can interrupt the target. A program blocked in `time.sleep`,
waiting on a socket, or inside a long-running C function produces no trace
event, and the request stays pending until one comes. It is not lost, but a
program whose work is one long sleep will look like the pause did nothing.
There is no mechanism in this design that could do better; both the module
README and `docs/debugging.md` now say so, in place of the entries that said
`pause` does nothing at all.
