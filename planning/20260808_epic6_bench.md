# EPIC-6 phase entry on a bench with hardware

Date: 2026-08-08
HEAD: 28591b41cc (micropython 2c816215dc, micropython-lib 5d4b78dd39)
Defect 5 and the criterion-1 section, same day, at HEAD 12bb383
(micropython 11828bf02e, micropython-lib 85ed324)

The work moved to a host with boards attached (the move the 2026-08-06 user
decision was waiting for). This records what the bench actually offers against
what EPIC-6's tickets assume, and the defects the first real board exposed.

## Bench inventory against the Q2 v1 board set

Q2 DECIDED the v1 firmware board set as unix, `rpi_pico_w`, `PYBD_SF6`,
`ESP32_GENERIC`. Of the three physical ones, one is present:

| Q2 board | bench label | state |
| --- | --- | --- |
| `PYBD_SF6` | `pybd` (PYBD-SF6W, STM32F767IIK) | connected |
| `rpi_pico_w` | `pico-w`, `pico2-w` | registered, offline |
| `ESP32_GENERIC` | `esp32-s3` | registered, offline (hub 1-1 port 2) |

Also connected: `wb55`, `wb55-hci`, `wb55-stlink`, `nrf52840-dk`,
`nucleo-h5-linked`, `pico-probe`, `ftdi-1v8`. Reachable over the pod tool:
`annealage-pod` with DUT `lab-nrf` (PCA10059 nRF52840) forwarded by usbip.

The user's standing constraint for this phase is that **PYBD-SF6W is the only
board that may be flashed**. `esp32-s3` has a switchable hub port recorded, so
it could be powered up, but bringing another owner's board out of a deliberate
unplugged state is not this phase's call.

Consequence for STORY-6.4: its acceptance list names ESP32_GENERIC and
rpi_pico_w scenarios that cannot run here. The list is not rewritten - those
criteria stay open and unmet, and the PYBD criteria become the ones this bench
can close. Per Q3, PYBD_SF6 is a multi-CDC board, so it exercises the
serial-DAP path; its WiFi also covers the network path, which leaves
ESP32_GENERIC's *single-UART, network-only* shape as the one transport
configuration with no substitute on this bench.

## Firmware chain, proven end to end

`firmware/firmware.toml`'s `stm32-pybd-sf6-debug` artifact was hash-verified
against its recorded sha256, flashed over mboot/DFU, and the board came back as
`v1.29.0-preview.gf9d7c96b96`, matching the manifest's `source_commit`. The CI
artifact is still valid for the current submodule pin: the only diff between
`f9d7c96b96` and the pinned tip outside `tools/mpremote` is
`docs/reference/mpremote.rst`.

The claimed capabilities then survived `capcheck.check_capabilities` against
the live runtime probe - but only after both defects below were fixed. Getting
that far is the whole point of the STORY-3.3 rule: a claim the probe disproves
is a hard error, and it fired.

## Defect 1: the installer's hardcoded `/lib` root

`ensure_debugpy_installed` wrote to `/lib/debugpy` and
`/lib/.debugpy-install.json`. On the PYBD the filesystem mounts at `/flash`:
`os.listdir("/")` is `["flash"]`, `sys.path` is
`["", ".frozen", "/flash", "/flash/lib"]`, and `os.mkdir("/lib")` raises
`OSError(19)` (ENODEV). The install failed outright, and had it somehow
succeeded nothing under `/lib` would have been importable.

Fixed by taking the install root from the target's own `sys.path`, the
resolution `mpremote mip` already uses (`mip.py:164-176`), with `device_dir`
and `marker_path` still overridable. Pinned by `TestDeviceLibDirResolution` in
`tests/test_s4_1_debugpy_install.py`.

This is a STORY-4.1 defect in a story marked DONE. Its ticket said installs
against a wiped device were exercised "against the unix port and fake
transports, not real hardware", with the device checks left to STORY-6.4 -
which is exactly where it surfaced. Both ports the fakes modelled (unix, and a
root-mounted board) share the one filesystem shape that hid the bug.

## Defect 2: `save_names` false negative from an `.mpy` install

With the install working, the probe reported `save_names: False` on firmware
that supports local names. Established on the board, in one interpreter
session: a source-compiled function's `f_locals` gives real names
(`['alpha', 'beta', 'f']`), while `probe_capabilities`, loaded from
`/flash/lib/debugpy/server/debug_session.mpy`, sees `local_N` placeholders.

Cause: local names live in the code object that declares them.
`probe_capabilities` read its *own* frame, so it measured whichever compiler
produced debugpy, not the firmware. mpy-cross does not persist names into
`.mpy` unless built with `MICROPY_PY_SYS_SETTRACE_LOCALNAMES_PERSIST`, which is
deliberately off (it corrupts line numbers - `20260706_recomposition.md`,
STORY-8.6). So every cross-compiled install reported False regardless of the
firmware, and the launcher rejected a manifest that was telling the truth.

Fixed by compiling a throwaway function at probe time and reading that frame,
falling back to the caller's frame where the firmware has no `exec`. Pinned by
`TestIntegration_RealUnixFirmware::test_capability_probe_survives_cross_compilation`,
which installs the real package as `.mpy` and compares the probe result against
the same firmware reading the source tree; it fails on the old probe.

This is the first consequence found of STORY-4.1's cross-compilation meeting
STORY-1.2's runtime probe. The user-facing half remains: a *target* program
deployed as `.mpy` still shows placeholder local names, because that is a
property of the user's own code objects and no probe changes it. That belongs
in the STORY-8.4 limitations section, not in the capability set.

## Defect 3: the DAP channel closed on every idle poll over WiFi

With the install fixed and the endpoint reported, the first session died
immediately after `initialize`: the host saw a broken pipe and the device
printed `wait_for_client: connection closed before configurationDone`. Nothing
had closed anything.

`JsonMessageChannel.recv_message` treated only EAGAIN (11) and EWOULDBLOCK (35)
as "no data yet" and closed the channel on any other `OSError`. Measured on the
board over its own WiFi socket, with the same 1 ms timeout `public_api.py` sets
after `initialize`:

| `settimeout` | errno raised by `recv` with no data |
| --- | --- |
| 0.001 | 110 (ETIMEDOUT) |
| 0.5 | 110 (ETIMEDOUT) |
| 0 | 11 (EAGAIN) |

lwIP reports an elapsed socket timeout as ETIMEDOUT, so the very first idle poll
closed the session - and since `public_api.py:62` drops the timeout to 1 ms as
soon as `initialize` is answered, that poll comes immediately. **The network
transport had never worked on a board.** Nothing caught it because the unix
port, which the entire host suite runs on, raises EAGAIN instead.

Fixed by naming the set (`_WOULD_BLOCK = (11, 35, 110)`) with the reasoning
attached. The same review found a second latent break in the write direction:
`send_message` called `sock.send()` once and ignored the returned count, so a
socket that accepted a prefix would truncate a frame mid-`Content-Length` and
desynchronise the stream with no protocol-level symptom - likely on a board,
where a `variables` response easily exceeds the window. Writes are now driven to
completion with a 5 s stall budget (the write runs inside the trace callback, so
an unbounded retry would wedge the debuggee, not just the channel), and
`StreamTransport.send` returns a byte count to match the socket contract it
claims to present.

Pinned by `tests/test_message_channel.py`, which drives the real module under
the unix firmware against sockets that behave the way a board's do; three of its
cases fail on the old code.

## Defect 4: clearing breakpoints left the debuggee's copy armed

`set_breakpoints` keeps each file's set under two keys - the path the client
sent and the name the debuggee reports for the same file - because
`should_stop` matches on `frame.f_code.co_filename`. It replaced the client
key unconditionally but only touched the debuggee key inside the per-breakpoint
loop. Two consequences: DAP's only way to remove breakpoints is a
`setBreakpoints` with an empty list, which left the debuggee key untouched and
the program still stopping at breakpoints the client had removed; and with
several breakpoints in one file the key was reset on each pass of the loop, so
only the last of them survived there.

Dormant on this bench: nothing configures `pathMappings` yet, so the two keys
are the same string and neither consequence can show. STORY-7.1's launch config
is what arms it. Found while writing the hardware scenario for `continue`,
which needs the clearing to work; fixed by replacing both keys together, and
pinned by `tests/test_dbg_07_clear_breakpoints.py`, which drives a real session
with `localRoot != remoteRoot` and fails on the old code.

## Defect 5: every DAP message over 1024 bytes desynchronised the serial link

Found bringing STORY-6.1's criterion 1 up on the board's second CDC. A session
over the stream handled small messages and then hung: `initialize` and
`setBreakpoints` answered, a breakpoint stopped the target, and an `evaluate`
returning a few hundred bytes came back at ~10 kB/s, but one returning 1024
bytes never answered at all and the link was dead afterwards.

Bisected by payload size rather than by reading code, then measured at the raw
layer with `pyb.USB_VCP(1).write()` and a plain `serial.Serial` reader on the
host: any write of 2048 bytes or more returns 1024. That is
`pyb_usb_vcp_write` → `usbd_cdc_tx_flow` → `usbd_cdc_tx`, which takes what fits
in `MICROPY_HW_USB_CDC_TX_DATA_SIZE` (1024 by default,
`mpconfigboard_common.h`) and reports that count. Not an error condition, and
not a board quirk: a short write is what the CDC interface does.

`StreamTransport.send` had a whole-buffer contract - loop until it all goes
out, raise on timeout. `public_api.py` drops the channel timeout to 1 ms once
`initialize` is answered, so the timeout expired mid-frame on every message
needing more than one write, and the raise discarded the count of what had
already gone. `messaging.py`'s `_send_all` then retried from offset 0 and
resent that prefix. The peer sees a Content-Length header followed by a body
with 1024 bytes repeated inside it, and nothing downstream resynchronises.

The fix is the socket contract: `send` writes once, returns the count, and
raises EAGAIN only when nothing went out. `_send_all` is the layer that knows
where the frame boundary is and was already written to drive one out from that
count.

Two things worth keeping from how this was pinned. The obvious test - put a
real `JsonMessageChannel` frame through a narrow pipe - passes on the old code
on a fast desktop, because the host drains quickly enough that several writes
fit inside the 1 ms budget and the frame completes in one `send`. It only fails
once the test stops draining mid-frame, which is what a USB turnaround does for
free on hardware. And a blocking POSIX pipe never short-writes at all: the
kernel loops. Reproducing the condition needs `O_NONBLOCK` on the write end and
`F_SETPIPE_SZ` to shrink it. Both are in
`tests/test_s6_1_stream_transport.py`; both halves of the assertion fail on the
old transport.

## Criterion 1: DAP over the board's own second CDC

With that fixed, `mpremote debug hil` against a `dap_device` target reaches a
breakpoint on the PYBD with no address of any kind. Three findings from wiring
it, each of which had to be got right independently:

- **The device chooses the channel, not the host.** `do_debug` sends
  `dap_stream="board"`. The host knows a tty node and the device knows a
  runtime object, and neither can name the other's. Passing the host's path
  down cannot work.
- **`pyb.USB_VCP(1)` constructing is not evidence.** It answers from
  `MICROPY_HW_USB_CDC_NUM`, a build-time maximum. What boot enumerated is in
  `pyb.usb_mode()`, whose name carries the count (`2xVCP+MSC`), so that is the
  test. `isconnected()` is not usable either: the host opens the interface only
  after reading the handshake this feeds, so it is False on every run that goes
  on to succeed.
- **A stream that cannot be produced must raise.** Falling back to TCP leaves
  the device reporting an endpoint the caller has no client for, because the
  caller is a bridge already waiting on the stream.

`caps["serial_dap"]` therefore means "this session took a stream", not "this
board has a spare CDC". It is False in a REPL probe on the same board, which is
why it stays out of `KNOWN_CAPABILITIES`: as a `requires` key it would fail
every target that named it, before the run that could satisfy it.

Throughput, which the risk register had open: 16 KB in 0.20 s, 81.7 kB/s. The
byte-at-a-time `recv` is not the problem on hardware that it is on a pty, where
a blocking read forced the loop in the first place. The write side was.

## Session semantics the hardware suite settled

Two behaviours that read as defects from the DAP side alone, and are not:

- **A breakpoint on a loop header fires on every pass.** Resuming from
  `target.py:80` produces another `stopped` at the same line, so a single
  `continue` buys one iteration of the body, not the rest of the program. Four
  stops for a three-iteration loop: the header is also reached once to set the
  loop up, before the first pass, so the body count lags the stop count by one
  throughout. `should_stop` has no notion of "we just resumed from here" and
  needs none - the line event fires once per execution of the line.
- **A second connection to the endpoint is refused mid-session.**
  `_accept_and_initialize` closes the listening socket once it has a client
  (`finally: listener.close()`), so the endpoint stops answering as soon as a
  debugger is attached. A prompt refusal is therefore the *expected* answer and
  is used as the independent liveness probe in the long-pause scenario: a
  refusal is the board's TCP stack replying, where a timeout would mean the
  link had gone away while the VM sat in the pause loop.

Measured with `MPY_DEBUG_HIL_PAUSE_SECONDS=60`: after 60 s stopped at a
breakpoint with no DAP traffic at all, the session's own socket still answered
a `stackTrace` and the board still refused a fresh connection promptly. The
risk-register question about the pause loop starving the WiFi driver is
answered for this board at that duration; longer holds are unmeasured.

## Also observed

- **A soft reset is what makes a device session repeatable, and it costs
  nothing here.** The Python-level `_listener` survives a finished session, so a
  second `mpremote debug` against the same board fails with `Already listening
  for debugger` until the VM is reset. Plain `mpremote debug <device>` already
  soft-resets on its first raw-REPL entry, which clears it. On this board that
  does not cost the network: the cyw43 link is driver state, so WLAN stays
  connected across the reset even though `boot.py` does not re-run (stm32 skips
  `boot.py`/`main.py` when the soft reset came from raw REPL). A port that keeps
  its WiFi state in Python would lose the interface there, so this is a
  per-port fact, not a general one.
- **Frames report a bare module path.** At a breakpoint in `/flash/target.py`
  the device reports `source.path` as `target.py`, the name the import
  resolved, not an absolute device path. A `pathMappings` entry with
  `remoteRoot: /flash` therefore matches nothing; the breakpoint that was hit
  had been set on the bare `target.py`. STORY-7.1's launch config and STORY-8.4's
  guide both need this to be right, and it is worth deciding whether the device
  should report an absolute path instead.
- `ensure_debugpy_installed` has no production call site. `do_debug` never
  invokes it (grep finds it only in `debugpy_install.py` and its tests), so
  `mpremote debug <device>` currently assumes debugpy is already installed.
  The installer is complete and now hardware-proven, but unreachable from the
  CLI. Raised as Q11.
- After an install, a `debugpy` already in `sys.modules` survives and shadows
  the new files. Any flow that installs and then starts a session in the same
  interpreter must soft-reset in between. Relevant to whatever wires Q11 up.
