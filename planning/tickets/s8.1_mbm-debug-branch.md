## Context

`andrewleech/micropython`, consumed by TWO integrations — ampremote (the user's
daily CLI) and this repo's `mpy-debugpy` micropython integration branch — so there

## Scope

In scope: create/push the branch, register it in ampremote's `mbm.toml`, add it to

## Files and anchors

- Branch creation pattern (`~/ampremote/CLAUDE.md`, "Adding a local-only branch"):
  branch from upstream master in the submodule
  (`git -C micropython checkout -b <branch> master`), push to the
  `andrewleech/micropython` fork.
- `~/ampremote/mbm.toml` — `[[submodules]]` path `micropython`, integration_branch
  `ampremote`; branches are `[[submodules.branches]]` entries with `name`,
  `pr_url`, optional `pr_number`, `title`. Local-only branches use a fork tree URL
  (pattern: `mpremote_raw_repl_retry` entry). **`ampremote_rename` must stay last
  in merge order** — insert the debug entry before it.
- `mbm add-pr` / manual-entry + rebuild flow: on conflict, resolve,
  `git merge --continue`, then fast-forward the integration branch
  (`git -C micropython branch -f ampremote <tip>`); rerere records resolutions.
- ampremote install model: `make install` in `~/ampremote` does
  `uv tool install --editable` of `micropython/tools/mpremote`, so once merged the
  command is live as `ampr debug` for hardware validation.
- This repo's side: the same branch becomes an entry in
  `/home/anl/mpy-debugpy/mbm.toml` under the micropython submodule (after
  `pdb_support` and the locals branch), so `mbm rebase` composes firmware debug
  support AND the mpremote command into one submodule checkout.

## Design constraints

- One branch, two consumers — never patch the command differently in the two
  integrations; fix on the branch and rebuild both.
- mpremote house style (per STORY-5.1 research): commands registered in the
  `_COMMANDS` dict in `micropython/tools/mpremote/mpremote/main.py`; handlers in
  `commands.py` take `(state, args)`; new-arg defaults preserve old behaviour.
- `ampremote_rename` stays last in ampremote's merge order.

## Approach sketch

1. Branch `mpremote_debug` (name it to match ampremote's `mpremote_*` convention)
   off upstream master on the fork; the EPIC-5 work lands there.
2. Register in `~/ampremote/mbm.toml` before `ampremote_rename`; rebuild the
   ampremote integration; `make install`; smoke `ampr debug --help`.
3. Add the entry to this repo's `mbm.toml`; `mbm rebase -s micropython`; verify
   `make firmware-unix` still builds (the branch only touches `tools/mpremote`,
   so firmware is unaffected — the value is one checkout carrying both).
4. Open the draft PR on `andrewleech/micropython` (base: the fork's master mirror)
   per policy; body references the mpy-debugpy planning docs.

## Revalidation and first attempt (2026-08-06, at HEAD 7fb63d3)

Authorisation is in place (the user confirms `~/ampremote` is a public
staging ground and adding in-PR branches there is normal). Two findings, one
of which stops this ticket short of done.

**Q1's "ONE branch" was right and the stack was wrong (corrected 2026-08-06,
commit 3e692f7).** The debug work had become five stacked branches. That
breaks mbm's model — a registered branch is a prospective PR, so it must sit
on upstream master; stacked, each one's diff carries its ancestors' and none
can be reviewed or merged alone, and each upstream move needs an ordered
rebase of the whole chain. Collapsed to `mpremote_debug` (six commits off
master) plus the genuinely independent `mpremote_debugpy_install`, with the
recomposed tree byte-identical.

**The rename-last violation is real and was fixable.** `mpr/fix_socket_rfc2217`
(#19062) sat after `ampremote_rename` in ampremote's `mbm.toml`. Moving it
before the rename and inserting the debug entries ahead of it produced a
correct ordering, verified by inspection.

**But the rebuild does not converge without resolving ampremote's own
conflicts.** `mbm rebase --local` walks the stack fine — reconnect,
resume-by-default, pty, file_cp_hash, smart-encoding, raw_repl_retry and
rfc2217 all integrate, several via rerere-staged resolutions concluded with
`git merge --continue` — and then hits a genuine unresolved conflict of 8
files at `mpremote_debugpy_install`: `console.py`, `transport.py`,
`transport_serial.py`, `tests/README.md`, `run-mpremote-tests.sh`,
`test_filesystem.sh`, `test_unicode.sh`(`.exp`).

**That first reading was wrong, and controlled experiments say so.** Three
hypotheses were tested and two killed:

1. *The stack causes it.* No — collapsing six branches to two reproduces the
   identical 8-file conflict.
2. *Base skew causes it.* ampremote's local `origin/master` was 356 commits
   stale, which looked promising. Fetching brought it to exactly the debug
   branches' base, zero skew — same conflict.
3. *ampremote's own stack is broken on current master.* No — the control run,
   the original `mbm.toml` with no debug entries on the freshly fetched
   master, **integrates completely cleanly**.

So adding `mpremote_debugpy_install` genuinely introduces it. But that branch
touches exactly three files against master — `debugpy_install.py` (new),
`mip.py`, `transport.py` — and none of `console.py`, `tests/README.md`,
`run-mpremote-tests.sh`, `test_filesystem.sh` or `test_unicode.sh(.exp)`,
which are five of the eight conflicted paths. A three-way merge cannot
conflict in a file only one side touched, so this looks like mbm's
rebase/merge mechanics for a branch whose base differs from the accumulating
integration, not a content clash between the changes.

That makes it a question about mbm rather than about the debug work, and mbm
is the user's tool — hence stopping here rather than resolving eight files by
guess.

ampremote was restored completely: submodule back at `5b459e2d57cc`, `ampremote`
branch unmoved, `mbm.toml` reverted, working tree clean. The pre-attempt tip
is also tagged on the fork as `ampremote-pre-debug-20260806`.

**To finish this ticket**, someone who owns those branches should either
resolve the 8-file conflict once (rerere will then replay it), or rebase the
debug stack onto ampremote's integration base so the collision does not
arise. Note also that ampremote's CLAUDE.md documents plain `mbm rebase`,
while this repo's documents `--local` because the bare form force-pushes at
upstream; `--local` was used here and should be adopted there too.

## DONE (2026-08-06)

The conflict was base skew after all, in a ref the earlier controls did not
check. mbm rebases every registered branch onto `upstream/master` and merges
the results; in `~/ampremote/micropython` that remote-tracking ref was still
at `4fd7295703` (2026-05-28), 356 commits behind real upstream. Hypothesis 2
fetched and compared `origin/master`, which is a different ref in that
submodule, so it read as "zero skew" while the ref mbm actually uses stayed
stale.

That explains the signature exactly. Every ampremote branch was being rebased
onto the stale base and so was mutually consistent — hence the clean control —
while the debug branches sit on current master. The eight conflicted paths are
precisely the mpremote files touched by the 356-commit gap: `console.py`,
`transport.py`, `transport_serial.py`, `tests/README.md`,
`run-mpremote-tests.sh`, `test_filesystem.sh`, `test_unicode.sh(.exp)`. It was
never a clash with what the installer branch changes.

`git fetch upstream` in the submodule, then `mbm rebase -s micropython
--local`, reduces it to four ordinary content conflicts, all in branches that
had never been rebased onto current master:

- #18436 and #18785 both predate upstream's `_quote_path` quoting; each keeps
  its own feature and adopts `_quote_path`.
- #18436 × #18785 collide for real in `fs_writefile` — both rewrote it. The
  composed version selects the encoding, then accumulates the device-side hash
  over the DECODED bytes so it stays comparable with the source hash.
- #19062 carries a duplicate `_wait_for_friendly_prompt` and a pre-resume-
  removal `main.py` command table; both defer to the composed versions.

**mbm's state-machine trap also fires on rebase conflicts, and silently.** It
prints `git rebase --continue` / `mbm rebase --resume` on a rebase conflict;
following that advice leaves `--resume` believing the branch is done and it
never merges it. The run then reports "All branches integrated" while three of
ten are missing from the tip — no warning, and the composed tree simply lacks
those features. Detected by containment (`git merge-base --is-ancestor`) and
by content (`compression_utils.py` absent, no `verify_hash` in
`transport.py`); the merge sequence was then replayed by hand in `mbm.toml`
order. Any future rebuild must verify containment rather than trust the
summary.

Result: ampremote `35d1533b47`, all ten branches contained, pushed to the fork
with the top-repo commit `e359b24`.

Verified behaviourally, not just structurally: `MPY_DEBUG_MPREMOTE_DIR` now
points this repo's DAP suite at any mpremote tree, and the whole suite passes
against the ampremote composition — 278 passed, identical to the standalone
tree. Two tests had to stop hardcoding a leading `resume`, which the
composition removes per #17485; `RESUME` resolves it per tree.
