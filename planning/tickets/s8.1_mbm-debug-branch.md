# mpremote/mbm: Register the `debug` command branch in ampremote AND this repo's integration

Phase: EPIC-8 / STORY-8.1
Depends on: EPIC-5 (the `do_debug` command exists — s5.1..s5.5); s8.5 (this repo's
  mbm composition wired, so the merge here is an mbm entry, not more hand-composition)
Written: 2026-07-06 at HEAD 59fab8450a (micropython 18c76f7c56; ampremote/micropython 5b459e2d57)

## Context

Q1 DECIDED (2026-07-06): the `debug` command develops on ONE branch on
`andrewleech/micropython`, consumed by TWO integrations — ampremote (the user's
daily CLI) and this repo's `mpy-debugpy` micropython integration branch — so there
is no divergence. Policy (from `~/ampremote/CLAUDE.md`): default to upstream; keep
a branch local-only while it needs hardware validation, raised as a draft PR on
the fork, base switched to `micropython:master` once validated (that retarget is
STORY-8.3 — intentionally inline-only in the roadmap, trivial).

## Scope

In scope: create/push the branch, register it in ampremote's `mbm.toml`, add it to
this repo's mbm composition, open the draft fork PR.
Out of scope: the command implementation itself (EPIC-5 tickets); upstream PR
retarget (STORY-8.3).

## Files and anchors

- Branch creation pattern (`~/ampremote/CLAUDE.md`, "Adding a local-only branch"):
  branch from upstream master in the submodule
  (`git -C micropython checkout -b <branch> master`), push to the
  `andrewleech/micropython` fork.
- `~/ampremote/mbm.toml` — `[[submodules]]` path `micropython`, integration_branch
  `ampremote`; branches are `[[submodules.branches]]` entries with `name`,
  `pr_url`, optional `pr_number`, `title`. Local-only branches use a fork tree URL
  (pattern: `mpremote_raw_repl_retry` entry). **`ampremote_rename` must stay last
  in merge order** — insert the debug entry before it.
- `mbm add-pr` / manual-entry + rebuild flow: on conflict, resolve,
  `git merge --continue`, then fast-forward the integration branch
  (`git -C micropython branch -f ampremote <tip>`); rerere records resolutions.
- ampremote install model: `make install` in `~/ampremote` does
  `uv tool install --editable` of `micropython/tools/mpremote`, so once merged the
  command is live as `ampr debug` for hardware validation.
- This repo's side: the same branch becomes an entry in
  `/home/anl/mpy-debugpy/mbm.toml` under the micropython submodule (after
  `pdb_support` and the locals branch), so `mbm rebase` composes firmware debug
  support AND the mpremote command into one submodule checkout.

## Design constraints

- One branch, two consumers — never patch the command differently in the two
  integrations; fix on the branch and rebuild both.
- mpremote house style (per STORY-5.1 research): commands registered in the
  `_COMMANDS` dict in `micropython/tools/mpremote/mpremote/main.py`; handlers in
  `commands.py` take `(state, args)`; new-arg defaults preserve old behaviour.
- `ampremote_rename` stays last in ampremote's merge order.

## Approach sketch

1. Branch `mpremote_debug` (name it to match ampremote's `mpremote_*` convention)
   off upstream master on the fork; the EPIC-5 work lands there.
2. Register in `~/ampremote/mbm.toml` before `ampremote_rename`; rebuild the
   ampremote integration; `make install`; smoke `ampr debug --help`.
3. Add the entry to this repo's `mbm.toml`; `mbm rebase -s micropython`; verify
   `make firmware-unix` still builds (the branch only touches `tools/mpremote`,
   so firmware is unaffected — the value is one checkout carrying both).
4. Open the draft PR on `andrewleech/micropython` (base: the fork's master mirror)
   per policy; body references the mpy-debugpy planning docs.

## Acceptance criteria and tests

- [ ] One branch on `andrewleech/micropython` is the sole source of the command.
- [ ] It builds into the `ampremote` integration via mbm with `ampremote_rename`
      last; `ampr debug --help` works from the installed tool.
- [ ] It is composed into this repo's `mpy-debugpy` micropython branch via mbm;
      `make firmware-unix` + `make test` stay green.
- [ ] Draft fork PR exists and links validation evidence expectations (STORY-6.4).

## Revalidation and first attempt (2026-08-06, at HEAD 7fb63d3)

Authorisation is in place (the user confirms `~/ampremote` is a public
staging ground and adding in-PR branches there is normal). Two findings, one
of which stops this ticket short of done.

**Q1's "ONE branch" is not what happened.** The debug work landed as a stack
of six: `mpremote_debugpy_install`, then
`mpremote_debug_command` -> `_targets` -> `_handshake` -> `_unix` ->
`_daplog`, each stacked on the last. That is better for review than one
squashed branch and it satisfies Q1's actual goal (no divergence between the
two consumers, since both compose the same tips), but the ticket's wording
should be read as "one lineage", not one ref.

**The rename-last violation is real and was fixable.** `mpr/fix_socket_rfc2217`
(#19062) sat after `ampremote_rename` in ampremote's `mbm.toml`. Moving it
before the rename and inserting the six debug entries ahead of it produced a
correct ordering, verified by inspection.

**But the rebuild does not converge without resolving ampremote's own
conflicts.** `mbm rebase --local` walks the stack fine — reconnect,
resume-by-default, pty, file_cp_hash, smart-encoding, raw_repl_retry and
rfc2217 all integrate, several via rerere-staged resolutions concluded with
`git merge --continue` — and then hits a genuine unresolved conflict of 8
files at `mpremote_debugpy_install`: `console.py`, `transport.py`,
`transport_serial.py`, `tests/README.md`, `run-mpremote-tests.sh`,
`test_filesystem.sh`, `test_unicode.sh`(`.exp`).

Most of those are not files the debug branches touch, so this is a collision
between ampremote's existing stack and the new branches' base, not something
the debug work introduces. Resolving it means making judgement calls about
the user's own in-flight branches (which side of a console/unicode-test
conflict is intended), which is beyond what "add an in-PR branch" authorises.

ampremote was restored completely: submodule back at `5b459e2d57cc`, `ampremote`
branch unmoved, `mbm.toml` reverted, working tree clean. The pre-attempt tip
is also tagged on the fork as `ampremote-pre-debug-20260806`.

**To finish this ticket**, someone who owns those branches should either
resolve the 8-file conflict once (rerere will then replay it), or rebase the
debug stack onto ampremote's integration base so the collision does not
arise. Note also that ampremote's CLAUDE.md documents plain `mbm rebase`,
while this repo's documents `--local` because the bare form force-pushes at
upstream; `--local` was used here and should be adopted there too.
