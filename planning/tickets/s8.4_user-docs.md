## Context

Today the usage story is scattered (repo README, debugpy module README, launcher
comments, VS Code configs). The end-user deliverable is ONE guide with one mental
model — resolve target → ensure runtime → sync → launch → attach — across the
three transports. The honesty constraint is the point: the old wrapper's docs and
variant names promised capabilities the firmware didn't have; this guide must
never claim what the runtime probe (`caps` in the MPDBG-READY handshake) would
contradict.

## Scope

In scope: one user-facing guide in this repo (and/or the debugpy module README
where content upstreams with s8.2), covering unix / serial / network transports,
the `mpdebug.toml` target model, firmware fetch vs build, and capabilities.
Out of scope: contributor/integration docs (CLAUDE.md, mbm) — already current;
extension marketplace copy (EPIC-7).

Rescoped 2026-08-09: firmware fetch vs build is a link, not a chapter -
`docs/firmware.md` covers variants, `fetch`/`verify`/`select`, per-port build
commands and the capability doctrine, and duplicating it would give the project
two capability tables to keep in step. The guide gains what did not exist when
this was written: the iteration loop (`--source` + `--loop`), `--dap-log`, and
the measured limitations under "Design constraints".

## Design constraints

- No capability claim the probe contradicts (STORY-8.4 acceptance; D4).
- Serial DAP is documented as multi-CDC-only, network as the primary device
  transport (D3/Q3); single-UART boards: network required, framing spike deferred.
  A `dap_device` target only takes the serial channel when the handshake also
  reports `serial_dap: true`; measured on PYBD_SF6 at 81.7-108.8 kB/s.
- v1 board set for prebuilt firmware: unix, rpi_pico_w, PYBD_SF6, ESP32_GENERIC (Q2).
- User CLAUDE.md language rules: factual, conservative; no "comprehensive".
- tty devices referenced as `/dev/serial/by-id/<name>` in every example.

Three measured limitations the guide must state, all found after this ticket was
written. Each is in the risk register; a guide that omits them is the exact
failure mode this story exists to prevent:

- **DAP `pause` answers success and never stops the target** (2026-08-09,
  STORY-4.5). A user pressing pause gets a UI that believes it is stopped while
  the program runs on.
- **A breakpoint inside a loop body stops one more time than the body runs, and
  the first stop is before the body has run at all**, so a variable the body
  assigns still reads its pre-loop value there
  (`20260809_settrace_line_event_fidelity.md`).
- **Local variables are read-only**, on every artifact, because no branch
  implements `_set_local`. The tooling greys them out from the probe rather than
  failing at write time.

Plus two session-shape facts a user hits in practice: ending a session by
signalling `mpremote` while the client still holds a paused target leaves a
device only a power cycle clears, whereas detaching the client first leaves a
responsive board (`20260809_story4.3_mount_teardown.md`); and `--loop` never
sends `terminated`, so the session outlives each run by design.

## Approach sketch

Structure: (1) 5-minute quick start on unix (zero hardware); (2) the mental model
(one diagram: resolve → ensure → sync → launch → attach; control plane vs data
plane); (3) per-transport pages sharing the same headings; (4) firmware: fetch
(manifest-verified) vs build (docker per s3.2); (5) capabilities: what the probe
reports and what each value means in the editor (greyed-out locals, placeholder
names); (6) troubleshooting keyed on actual failure modes (stale device code →
staleness guard message; no `stopped` event → firmware without settrace, probe
output shown). Write against the real commands; every snippet must be paste-able
and tested.

Revised 2026-08-09. One page, `docs/debugging.md`, linked from the README, with
sections in the order a user meets them: quick start on unix; the target file;
the mental model (control plane = raw REPL over the connect string, data plane =
whatever endpoint the handshake reports, and the user types neither); the three
transports under shared headings; the iteration loop (`--source`, then `--loop`);
attaching from VS Code, naming what the extension cannot pass; what the probe
reports and what each value means in the editor; limitations, stated as measured
behaviour with the measurement named; troubleshooting, quoting the actual error
strings from `commands.py` so a user can search for what they saw. Firmware is
one paragraph plus a link. `--dap-log` belongs in troubleshooting, not in its own
section - it is what a user reaches for when nothing else explains the failure.
