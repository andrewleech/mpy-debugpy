# mpremote+debugpy: Hot-reload iteration loop via sys.modules eviction + re-import

Phase: EPIC-4 / STORY-4.5
Depends on: STORY-2.1 (DONE, D2), s4.1 (debugpy present on device), s4.3 (establishes the mount); interacts with s5.3/s5.4 session lifecycle
Written: 2026-07-06 at HEAD 59fab8450a (micropython 18c76f7c56, micropython-lib 0d42fcd5bc; ampremote/micropython 5b459e2d57)
Revalidated: 2026-08-08 at HEAD 2a465a7 (micropython bbdefbc3e8, micropython-lib 85ed324) - the mount this depends on is now s4.3's, and `mpremote mount` itself had to be repaired first; the eviction mechanism is confirmed on a PYBD_SF6; all launcher and transport anchors moved; no longer hardware-gated. ## Context

Surfaced by SPIKE-2.1 ("Follow-up stories", `../SPIKE-2.1-mount.md`): with source
mounted from the host, the only thing standing between "edit a file" and "debug the new
code" is MicroPython's import cache — evict the target module(s) from `sys.modules` and
re-import, and the mounted edit takes effect with NO upload and NO soft-reset. This
makes mount + re-import the mainline device iteration loop (D2's corrected framing).
The one hard limit is ordinary import-caching semantics: an already-paused frame runs
already-compiled bytecode; edits apply from the next (re-)import, never inside the
current frame.

## Scope

In scope: a restart affordance in the debug flow — on session restart (DAP `restart`
request and/or a `do_debug` loop mode), evict the target module and its project-local
imports from `sys.modules`, then re-import and re-run the target, keeping the DAP
listener and mount alive.
Out of scope: live-patching the currently paused frame (impossible — set expectations
in UX text); the Debug Console monkey-patching path (s6.5); establishing the mount
(s4.3).

## Files and anchors

Verified at HEAD 2a465a7 (micropython bbdefbc3e8, micropython-lib 85ed324):

- Launcher run-target path: `launcher/mpy_launch_debugpy.py:190`:
  `target = __import__(target_module, None, None, ("*",))`, then `:195`
  `getattr(target, target_method, None)` and the call at `:199`. The restart loop wraps
  exactly this: evict → `__import__` again → call again. The `MPDBG-READY` handshake
  (`:173`) must be emitted ONCE per process, not per iteration. The import already sits
  behind `wait_for_client()` (`:176`) and `debug_this_thread()` (`:184`), so an
  iteration must not re-run either.
  `micropython/tools/mpremote/mpremote/mpy_launch_debugpy.py` is a byte-identical copy
  shipped inside the mpremote package; both move together.
- Eviction semantics: confirmed on a PYBD_SF6 with a host directory mounted at
  `/remote` - `del sys.modules[name]` then re-import re-reads the mounted file
  (`../20260808_epic4_phase_entry.md`). The fs hook's `os.chdir('/remote')` makes the
  module resolve there with no `sys.path` change.
- Mount mechanics (host side): `micropython/tools/mpremote/mpremote/
  transport_serial.py:347` `mount_local`, `:445` `umount_local`, `:1047`
  `SerialIntercept`; the mount survives across re-imports because any read on the
  transport services fs-RPC (the core SPIKE-2.1 finding). s4.3 is what establishes it in
  the debug flow; nothing in `do_debug` mounts anything today.
- DAP restart: the debugpy server (`debugpy/server/debug_session.py`) has no `restart`
  handler, and `supportsRestartRequest` is present but commented out at `:373`.
  Adding one is the clean trigger; a command-side "watch + restart" loop is the
  alternative that needs no server change.

## Design constraints

- Breakpoints must survive a restart: the DAP client re-sends setBreakpoints on a new
  session, but if we keep ONE session alive across re-imports, the server's existing
  breakpoint table persists — prefer that (cheaper on-device, no re-attach latency).
- Eviction set: the target module plus modules whose `__file__` sits under the project
  source root(s) (from s5.2's target model). Never evict `debugpy.*` or stdlib —
  evicting the running debugger is self-destruction.
- The trace function must be re-installed (or confirmed still installed) after
  re-import; `debug_this_thread()` is idempotent enough today but verify.
- No soft-reset: `machine.soft_reset()` would drop the mount and the socket; the whole
  point is avoiding it.
- The device only sees an edit once the host has closed the file. A write that goes
  through the mount from the device side is re-read truncated until close, because the
  host end of the RPC buffers it; an editor saving on the host is fine, but any test
  that stages an edit through the mount must close before triggering the restart.

## Approach sketch

1. Launcher grows a loop mode: run target → on completion or on an explicit restart
   command (DAP `restart` request, or a sentinel over the control channel), evict the
   project module set from `sys.modules`, re-import, re-run. Emit a per-iteration
   marker line (NOT another MPDBG-READY) so the host knows a restart happened.
2. Server side (preferred trigger): handle the DAP `restart` request — respond, unwind
   out of the paused poll loop cleanly (set continue + a restart flag the launcher
   checks), and let the launcher loop do the eviction. Advertise
   `supportsRestartRequest: true` in the initialize response only when launched in loop
   mode.
3. Command side (s5.x): `mpremote debug --loop` keeps the session attached across
   restarts; document that VS Code's restart button now "just works" on mounted
   targets.

## Acceptance criteria and tests

- Mounted flow over a pty-backed unix firmware: edit a source file on the host after the
  first run completes, trigger restart, hit a breakpoint on a line that only exists in
  the edited file, proving fresh source ran, with no upload and no reset.
- Breakpoints set before the restart still bind after it (same session kept alive).
- `debugpy` module itself is never evicted (assert eviction set contents in a unit
  test).
- A paused session + edit + restart: the paused frame's code is unchanged until
  restart, then the new code runs — matches the documented semantics.
- Adversarial: target module imports a submodule that ALSO changed — both are evicted
  and both re-read (eviction-set correctness, the classic hot-reload hole).
- Adversarial: a restart while the target is paused inside the changed module, and a
  restart requested twice before the first completes.

## Execution progress

**DONE 2026-08-09** at HEAD 878c9bc (micropython 49502103e3, micropython-lib
84aaf65). Design, measurements and the deviations from this ticket are in
`../20260809_story4.5_hot_reload.md`; the two VM findings have their own notes,
`../20260809_settrace_raise_unwind.md` (fixed) and
`../20260809_settrace_line_event_fidelity.md` (characterised, not fixed).

All six acceptance criteria are covered by `tests/test_s4_5_hot_reload.py`, four
tests over a live pty-backed session with `mpremote resume debug --loop --source`
as its own subprocess. Criterion 3 (`debugpy` never evicted) is asserted from the
restart marker's own eviction list rather than in a separate unit test, so what
is checked is what the device did, not what a helper would do if called.

Three things landed differently from the sketch above:

- **The eviction set is a snapshot diff of `sys.modules`, not "modules whose
  `__file__` sits under the project source root".** MicroPython does set
  `__file__`, but on a mounted session it reads as the device path
  (`/remote/app.py`), so the path rule would need the client's mapping applied
  to answer a question the device must answer alone. The diff also makes "never
  evict the debugger" structural rather than a blacklist.
- **`RestartRequest` derives from `BaseException`.** The trigger is the DAP
  `restart` request as recommended, and the unwind is a raise from the trace
  function, so a target's `except Exception:` would otherwise swallow the
  restart and leave it silently undone. That raise is also what exposed the
  `mp_prof_is_executing` defect, which had to be fixed before this story could
  work at all rather than appear to.
- **Run boundaries are mirrored to the client's debug console**
  (`debugpy.console()`, a DAP `output` event). The marker on device stdout was
  invisible on exactly the transport this story is about: a mounted session's
  filesystem pump discards everything the device prints. `terminated` is still
  never sent in loop mode - a client that sees it tears the session down.

Found and not fixed, recorded in the risk register: the DAP `pause` request
answers success and never stops the target.

## Open questions

  watch loop was built. `--loop` is what makes a session advertise
