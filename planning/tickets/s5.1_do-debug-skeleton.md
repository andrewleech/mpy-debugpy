## Design constraints

- ampremote house style (from `~/ampremote/CLAUDE.md`, verbatim rules): inline byte
  literals with trailing intent comments (no control-byte constants); prefer extending
  the existing `read_until` / `exec` primitives over new abstractions; new parameters on
  existing methods default to previous behaviour; single-caller helpers get a leading
  underscore.
- Upstream-first (D1/EPIC-8): code must be upstreamable as-is — no `ampremote`-specific
  naming (`ampremote_rename` handles branding separately and stays last in mbm order).
- Endpoint truth comes from the device (`MPDBG-READY`), never from user config
  (design position; enforced by s5.4).
- The debugpy server is single-threaded/poll-driven — the command must not assume it
  can talk DAP before the client attach phase; the boot script blocks in
  `wait_for_client()` until `configurationDone`.

## Approach sketch

1. `argparse_debug()`: description "debug a MicroPython script with a DAP client";
   positional `target` (name from `mpdebug.toml`, resolved in s5.2 — until then accept
   `unix` or a serial connect string), optional positional `program`
   (`module[:method]`, default `target:main` matching the launcher's defaults),
   `--port` (int, default 0 = device-assigned), `--dap-log` (declared, wired in s6.3).
2. `do_debug(state, args)`: parse `module[:method]`; branch on target kind. For the
   serial stub: `state.ensure_raw_repl()`, `state.did_action()`, upload/exec the boot
   script with args via the `_do_execbuffer` shape, read output lines until
   `MPDBG-READY ` prefix, `json.loads` the remainder, print endpoint+caps. Unix branch
   raises "see s5.3" NotImplemented-style `CommandError` until s5.3 lands.
3. Keep the handshake-read helper private (`_read_mpdbg_ready(...)`) — single caller
   now; s5.4 will generalise it across control planes.
4. Commit on branch `mpremote_debug_command` off upstream master in the submodule
   (Q1 layout; registration into both integrations is s8.1).

## Acceptance criteria and tests

- [ ] `mpremote debug --help` lists the command with a real description (auto-derived
  from `argparse_debug`), and `mpremote help` shows it in the command list.
- [ ] `mpremote debug` with a connected device reaches the boot script and prints the
  parsed endpoint + capability dict from the `MPDBG-READY` line (no IP/port literals
  anywhere in the code path).
- [ ] house-style conformance: no new abstraction layer duplicating `exec`/`read_until`;
  single-caller helpers underscored; new args default to old behaviour.
- [ ] `state.did_action()` is called — the session does not drop into the REPL after
  the command completes.
- Adversarial: malformed `module[:method]` (empty method, extra colons) yields a
  `CommandError` with usage text, not a traceback; a target that never prints
  `MPDBG-READY` times out with a clear error naming the expected line.

Three review rounds ran. The blocking finding is architectural, not
cosmetic: the story's "print the parsed endpoint from `MPDBG-READY`"
criterion is unreachable because `debugpy.listen()` only returns — and the
launcher only prints the handshake line — after a DAP client has attached.
Recorded as Q8 with the fix shape in
`20260805_handshake-ordering-blocker.md`. s5.1 cannot meet its acceptance
criteria until that micropython-lib change lands, so it stops here rather
than shipping a command whose documented success path cannot be reached.

Two further findings worth carrying (both verified, neither fixed yet):

- mpremote appends a `nargs=REMAINDER` `next_command` positional to every
  parser, so for a command with an optional trailing positional, any option
  written *after* the positionals is silently swallowed — `debug <dev>
  mod:main --timeout 8` waits the default 60s and later reports
  `'--timeout' is not a command`. Upstream-wide trap (`run --no-follow` has
  it); needs the option-order convention documented in the command help plus
  tests that assert a flag actually takes effect, not merely that `--help`
  lists it.
- An early device exit stalls for the whole timeout and reports `'>'`
  instead of the device's own error, because the raw-REPL tail after a clean
  return is `\x04\x04>` with no newline, so `read_until(1, b"\n")` waits out
  its inter-character budget. Assemble lines locally, break on either `\n`
  or `\x04`, and quote the last device line in the error.

Both carried findings are now fixed (2026-08-05) and the branch is pushed as
`andrewleech/micropython` `mpremote_debug_command` @ `f240be068a`:

- The device's exception text now reaches the error. The earlier attempt only
  quoted the stdout channel, which is empty in the most common failure (a
  top-level `import debugpy` on firmware without it), so the message was
  `last output: ''`. `_mpdbg_error` reads the exception chunk that follows the
  first `\x04` and quotes it.
- The command's description was 150 characters and wrecked the aligned
  two-column `mpremote help` table; it is now one short line with the
  option-ordering caveat moved to the parser epilog.
- Docs and `--help` now mark `unix` and `--dap-log` as not yet implemented,
  the timeout error quotes partial output too, and the `--port 5678` literal
  carries a comment tying its removal to the Q8 fix.

Coverage is 17 tests (full suite 99 passed / 1 xfailed, up from 82). Two are
real-pty cases against the unix firmware: that `--port`/`--timeout` before the
positionals take effect, and that a device without debugpy reports its
ImportError. Both new tests were confirmed to fail against the unfixed code.

`mbm.toml` is deliberately unchanged and the integration branch is not moved —
registering a command whose documented success path is unreachable would be
