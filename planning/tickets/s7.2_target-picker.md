# extension: Status-bar target picker over `mpdebug.toml` with honest capability display

Phase: EPIC-7 / STORY-7.2
Depends on: s7.1 (the provider the picker feeds), s5.2 (`mpdebug.toml` named-target format — that ticket owns the schema)
Written: 2026-07-06 at HEAD 59fab8450a (micropython 18c76f7c56, micropython-lib 0d42fcd5bc)

## Context

With s7.1 in place, F5 debugs "the target" — this ticket supplies the UI for choosing
which target, and surfaces what the chosen firmware can actually do. Honest capability
display is a settled design rule (D4, STORY-1.2): capability comes from the runtime
probe, never from a variant/target name. `ROADMAP.md` STORY-7.2. STORY-7.3 (collapse
legacy launch.json/tasks.json) is inline-only in the roadmap (trivial) and lands with
s7.1, not here.

## Scope

In scope: a status-bar item listing the named targets parsed from the project's
`mpdebug.toml`; the selection persists (workspaceState) and drives which target s7.1's
resolver launches; after a session's handshake arrives, the probed capability summary
is shown honestly (e.g. "locals: placeholders", "local edit: unsupported").

Out of scope: the `mpdebug.toml` schema and resolution semantics (owned by s5.2 in the
mpremote command — the extension only *reads* target names, it never resolves
transports); editing/creating targets from the UI (defer; users edit the TOML).

## Files and anchors

- `mpdebug.toml` — format owned by ticket s5.2 (`kind = unix|serial|network`, connect
  string via `/dev/serial/by-id/...`, firmware/capability requirement). The picker
  needs only the target names + `kind` for display; re-resolve this anchor at phase
  entry once s5.2 has landed.
- `caps` dict fields, verified against
  `micropython-lib/python-ecosys/debugpy/debugpy/server/debug_session.py:82`
  (`probe_capabilities()`): `settrace`, `save_names`, `set_local`, `f_back` — booleans.
  Reaches the extension in the `MPDBG-READY` payload
  (`launcher/mpy_launch_debugpy.py:90`) parsed by s7.1's handshake parser.
- Display mapping (capability → user-facing text):
  `save_names: false` → "locals: placeholder names (local_N)";
  `set_local: false` → "local edit: unsupported (globals editable)";
  `settrace: false` → target not debuggable — picker marks it and F5 fails early
  with the firmware guidance message.
- New code: `extension/src/targetPicker.ts` + wiring in `extension/src/extension.ts`
  (s7.1's tree).

## Design constraints

- Never display a capability the probe would contradict (STORY-3.4/8.4 AC language);
  before the first handshake of a session the picker shows the target as "capabilities
  unprobed", not optimistic defaults.
- The extension does not parse/validate transport details from `mpdebug.toml` beyond
  names and `kind` — resolution is the command's job (D1). A missing/ambiguous file
  shows a actionable message ("no mpdebug.toml — run `mpremote debug --init`" or the
  s5.2-equivalent), not a stack trace.
- Selection must also be settable per-launch via a `target` attribute in a
  launch.json config (picker is the default, not the only path).

## Approach sketch

`vscode.window.createStatusBarItem` showing `$(debug-alt) <targetName>`; click opens a
QuickPick built from the parsed TOML (`kind` as description). Store the pick in
`workspaceState`. s7.1's resolver reads the stored pick when the launch config has no
explicit `target`. After s7.1 parses a handshake, publish the caps via an event; the
picker appends a one-line capability summary to the status-bar tooltip and (first time
per target per session) a subtle notification if `save_names` is false — the "you are
seeing placeholder names" surprise is the one worth interrupting for. Parse TOML with
a small vendored parser or `@iarna/toml` (record the choice in the PR).

## Acceptance criteria and tests

- [ ] picker lists exactly the targets in `mpdebug.toml`; selection drives F5.
- [ ] selected target survives a window reload (workspaceState).
- [ ] capability summary appears after attach and matches the handshake caps verbatim
  (test with a `save_names: false` firmware — placeholder wording shown).
- [ ] no `mpdebug.toml` / malformed TOML → actionable message, F5 still usable with an
  explicit `target` attribute.
- [ ] adversarial: a target whose name lies (e.g. "set_local" in the name) displays
  only probed truth.

## Revalidation (2026-08-07, phase entry at HEAD 9a9e6e1)

s5.2 has landed, so the schema anchor resolves. `mpdebug_config.py` defines
`[target.<name>]` flat tables with `kind` in `unix|serial|network` (required),
optional `device`/`firmware`/`program` strings, and `requires` as a list drawn
from `KNOWN_CAPABILITIES = ("settrace", "save_names", "set_local", "f_back")`.
Unknown keys are ignored by design, "so a front-end can store its own metadata
(icons, ordering, ...) alongside these" — this picker is that front-end.

**Discovery is the part that needs care.** `find_config` walks from the cwd
upward, stopping above `$HOME` and at any directory holding `.git` (as a
directory or a `gitdir:` file, so worktrees count). The command exposes no
machine-readable list of targets, so the picker has to mirror that walk in
TypeScript, which is duplicated logic that can drift. Mirror it, keep the
duplication explicit in a comment, and cross-check the two implementations in
a test over fixture trees rather than trusting them to stay in step.

s7.1 landed the pieces this ticket plugs into: the resolver already accepts a
`target` attribute (so the "picker is the default, not the only path"
constraint is already satisfied), and `summarizeCapabilities` in `config.ts`
already turns a probed `caps` dict into honest text and is unit-tested. This
ticket adds the status-bar surface and the persisted selection, and feeds the
caps summary to it after a handshake.

This repo has no `mpdebug.toml`, so its own default path is the
no-config-file one. That makes the "actionable message, F5 still usable with
an explicit `target`" criterion the case exercised by default here — and
`.vscode/launch.json` already sets `target: "unix"` explicitly, which must keep
working untouched by the picker.

## DONE (2026-08-07)

`targets.ts` (pure) mirrors `find_config`'s upward walk and `_load_targets`'s
validation, returning a typed result rather than throwing a parser error at the
UI; `targetPicker.ts` is the status-bar surface, the QuickPick, and the
`workspaceState` selection. TOML via `smol-toml` (no runtime deps, ships its own
types), in `dependencies` — an extension ships what it needs at runtime.

The mirrored discovery is cross-checked against the real Python, not against
itself: fixture trees are handed to both `mpdebug_config.find_config` and
`_load_targets` and to the TypeScript, and the answers must match — config in a
parent, a `.git` directory barrier, a `gitdir:` file barrier, the `$HOME`
boundary, nothing found, plus unknown `kind` and unknown `requires`. That is the
guard against the duplication drifting.

Capability text comes only from the probe. Before a handshake a target reads
"capabilities unprobed"; `reportSessionStart` drops a target's cached probe as a
new session begins, so an earlier session's result is never presented as
current; and where no picker selection matches, the tooltip names which target
the displayed probe actually came from rather than implying it describes the
selection. A target named `set_local` whose probe says `set_local: false`
displays read-only — asserted.

Two acceptance criteria were confirmed by mutation rather than by reading, both
having been untested when first written: inverting `config.target ??
picker.selectedTarget` fails the precedence test, and replacing `workspaceState`
with an instance field fails the persistence test. Suites: 80 node, 10
extension-host, 279 pytest.

Departures from the ticket, both deliberate:

- The suggested message "run `mpremote debug --init`" names a flag that does not
  exist. The no-config message says to add a `[target.<name>]` table or set an
  explicit `target` in `launch.json`.
- "Survives a window reload" is proven as far as one host process allows: the
  value is asserted in the `workspaceState` memento itself, not just read back
  through the getter. Proving the reload would need a second Extension
  Development Host; the memento is the thing VS Code persists, so this is the
  boundary and the test says so.

Known limitation, flagged rather than fixed: the picker discovers from
`workspaceFolders[0]` while the resolver spawns in `config.cwd`. Identical for
this repo and any single-root project whose config uses `${workspaceFolder}`;
they can diverge in a multi-root workspace or with a custom `cwd`. Mirroring
"the resolver's cwd" needs a UI decision about which launch config applies when
several differ, which is a design question this ticket should not settle alone.
The QuickPick title shows the discovered config path so a mismatch is visible.

Also fixed here: activation was briefly `onStartupFinished`, which put a
status-bar item into every VS Code window including projects with no MicroPython
in them. It is `workspaceContains:mpdebug.toml` alongside the two debug events.
