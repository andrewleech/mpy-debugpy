# extension/CI: Extension-host smoke test — resolver yields a valid attach and reaches a breakpoint on unix

Phase: EPIC-7 / STORY-7.4
Depends on: s7.1 (the provider under test); built unix firmware + working `mpremote debug` (EPIC-5) available in CI
Written: 2026-07-06 at HEAD 59fab8450a (micropython 18c76f7c56, micropython-lib 0d42fcd5bc)

## Context

EPIC-7's provider (s7.1) is glue between three moving parts (mpremote child process,
handshake contract, ms-python.debugpy attach); glue is where regressions hide. The
repo's testing rule (`CLAUDE.md`): tests drive real behaviour, not source-string
checks, and stay machine-independent. STORY-7.3 is inline-only in the roadmap
(trivial, lands with s7.1); it needs no test beyond "the old hacks are gone".

## Scope

In scope: an automated extension-host test (`@vscode/test-electron`) that (a) unit-tests
the handshake parser as pure functions, and (b) end-to-end: starts a `micropython`-type
debug config against a unix target, asserts the resolver spawned the command, parsed
the handshake, started a `debugpy` attach session, and a breakpoint in
`src/target.py` is hit. Headless CI wiring (xvfb on linux).

Out of scope: device-transport tests (s6.4 owns hardware-in-loop), picker UI tests
beyond selection persistence (s7.2's unit tests), performance.

## Files and anchors

- `extension/src/handshake.ts` (created by s7.1) — the pure parser under unit test;
  contract: consume exactly one `MPDBG-READY {json}` line
  (`launcher/mpy_launch_debugpy.py:90` — fields `host`, `port`, `caps` with boolean
  `settrace`/`save_names`/`set_local`/`f_back`), ignore all other stdout noise
  (banner text precedes it, `:70-78`).
- `src/target.py` — the sample debuggee the E2E test breaks in; the existing host
  harness (`tests/test_epic1_foundations.py:109`) breaks at line 80 because the
  `line` event fires BEFORE the statement executes — reuse the same line-choice
  rule (break after an assignment, never on it).
- `tests/` — the existing pytest DAP harness (fake VS Code) is the behavioural
  reference for what a correct attach/stop looks like; the extension test asserts the
  same observable outcome through the real VS Code debug API
  (`vscode.debug.onDidStartDebugSession`, `onDidChangeActiveDebugSession`,
  breakpoint hit via `vscode.debug.activeDebugSession` + DAP `stopped` tracker).
- New code: `extension/src/test/` (test runner + suites), CI job in the repo's
  workflow (xvfb-run; cache the VS Code download).

## Design constraints

- Machine-independent: no absolute paths; firmware located the same way the pytest
  harness does (`MPY_DEBUG_FIRMWARE` env var, falling back to
  `micropython/ports/unix/build-standard/micropython` — see
  `tests/fixtures/debuggee.py`).
- The E2E test must fail (not skip) if `ms-python.debugpy` is missing — that IS the
  dependency declaration under test. Install it into the test host
  (`--install-extension ms-python.debugpy`) in the runner.
- No sleeps for synchronisation: await debug-API events with bounded timeouts
  (mirror the server's 30 s `WAIT_FOR_CLIENT_TIMEOUT_S`).

## Approach sketch

Two layers. Unit: mocha suites over the handshake parser (valid line, noise-wrapped
line, split-across-chunks line, garbage JSON, no line → timeout error). E2E: a
`DebugAdapterTrackerFactory` registered for `debugpy` records DAP events; the test
sets a breakpoint in `src/target.py`, calls
`vscode.debug.startDebugging(ws, {type: "micropython", name: "test", request: "launch", target: "unix", ...})`,
then awaits the tracker seeing a `stopped` event with reason `breakpoint`, then
disconnects and asserts the mpremote child exited. CI: linux job, xvfb-run,
`make firmware-unix` prerequisite shared with the existing test job.

## Acceptance criteria and tests

- [ ] parser unit suite green, including the adversarial inputs above.
- [ ] E2E: resolver-started session reaches a `stopped`/`breakpoint` on unix with zero
  hand config; child process cleaned up after disconnect.
- [ ] suite green headless in CI (xvfb), using the same firmware artifact as
  `make test`.
- [ ] a deliberately broken handshake (env-var fault injection or a stub command)
  produces the s7.1 diagnostic error path, asserted.

## Workflow shape

Test authoring on haiku, with sonnet for the extension-host runner/CI plumbing if it
grows; opus review focuses on flakiness (event races, timeouts) — flaky debug-API
tests are worse than none.

## Open questions

## Revalidation (2026-08-07, phase entry at HEAD 279f1ad)

**The unit layer this ticket describes already landed with s7.1**: 45
`node:test` cases over `handshake.ts`, `config.ts` and `command.ts`, including
the noise-wrapped, split-across-chunks, garbage-JSON and no-line-then-timeout
cases named here, plus an integration test that drives the real
`mpremote debug unix` and one that does it through the checked-in
`.vscode/launch.json`. So this ticket reduces to the extension-host layer.

That layer is what pays for itself, because s7.1 left exactly two things
unproven and both live only inside a running host:

- whether the Dynamic-trigger provider registration actually activates
  (`onDebugDynamicConfigurations:micropython` is declared, never exercised);
- whether the `mpyDebugLaunchId` marker survives ms-python.debugpy's own
  resolver. The port-based fallback in `matchesLaunch` exists because it may
  not, and nothing has yet established which path is taken - so nothing has
  established that ending a session terminates its child.

The environment supports it, verified rather than assumed: `@vscode/test-electron`
downloads VS Code 1.132.0, `xvfb-run` is present, and
`--install-extension ms-python.debugpy` succeeds from the marketplace (it
pulls ms-python.python and pylance with it). One WSL-specific trap: the CLI
prompts "please install Visual Studio Code in Windows" and blocks on stdin
unless `DONT_PROMPT_WSL_INSTALL=1` is set. Set it unconditionally in the
runner; it is inert elsewhere.

The existing node suite uses `node:test`, not mocha. The host suite needs its
own runner regardless (it runs inside the extension host), so both stay -
`npm test` for the pure/integration layer, a separate script for the host
layer, which is too slow and too heavy to sit in the default suite.

## DONE (2026-08-07)

`extension/src/test/host/` runs a real Extension Development Host (VS Code
pinned to 1.132.0, `ms-python.debugpy` force-installed into it) over this
repo's own root as the workspace, so `.vscode/launch.json` is driven exactly
as a user's F5 drives it. `npm run test:host`, kept out of the fast `npm test`
glob; a CI job builds its own unix firmware and runs it under xvfb.

Five tests. What they establish, and what they do not:

- **Breakpoint, with location.** A `stackTrace` request asserts the top frame
  is `src/target.py:78`, not merely that some `stopped` event arrived — the
  first version passed with `pathMappings` removed entirely.
- **Dynamic-trigger activation is real.** `workbench.action.debug.selectandstart`
  with an explicit type calls the matching Dynamic provider's `pick()`, and the
  quickpick is driven to completion. The first version only checked
  `ext.isActive`, which flips from the declared activation event whether or not
  any Dynamic provider is registered — it passed with the registration deleted.
- **Correlation: `mpyDebugLaunchId` survives ms-python.debugpy's resolver**, so
  `matchesLaunch`'s first branch is what correlates. The port fallback is
  therefore untaken in this VS Code/debugpy version; it stays as insurance and
  is now asserted on, so a future debugpy that strips the marker fails here
  rather than silently switching branches.
- **No child outlives its session** — the real pid, from `/proc`, scoped to
  direct children of the extension host.

**What this suite cannot prove, verified rather than assumed:** that the
extension's own `terminateChild` is what reaps the child. On the unix flow the
reap is over-determined — ms-python.debugpy's `disconnect` reaches the
on-target server, which closes the channel regardless of `terminateDebuggee`,
and the launcher exits. Deleting `terminateChild` from
`onDidTerminateDebugSession` leaves this suite green (confirmed directly, with
a debuggee that loops forever after the breakpoint so it cannot self-finish).
The acceptance criterion — ending the session terminates the child — holds.
The stronger attribution does not, and cannot on this transport without
changing submodule behaviour. `terminateChild` earns its place on the path
where the command outlives the device's session (`--dap-log` keeps mpremote
alive as a proxy after a serial/network target disconnects); proving that
needs STORY-6.4's hardware, and is flagged there.

One stability fix found by running it repeatedly: the termination test
originally stopped `vscode.debug.activeDebugSession`, which is whatever VS
Code last focused. Under load that was intermittently the wrong session,
leaving the debuggee attached and leaking the child. It now stops the session
it started, identified by the launch marker. Sixteen runs since, including two
concurrent with the full pytest suite, all green with no strays.
