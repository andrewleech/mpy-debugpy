## Context

Two chronic failure modes from the old wrapper: debugging stale device code without
knowing (silent `cp -r` skipped, or interrupted), and hand-written `pathMappings` in
nine `launch.json` configs with relative/ambiguous roots that break in multi-root
workspaces. This ticket makes staleness loud and pathMappings generated — both derived
from the sync/mount record the command already has, never typed by a user.

Constraining decisions: D2 (mount mode makes staleness structurally impossible — the
guard is trivial there), D1 (all logic in the command, not the editor).

## Scope

In scope: (a) establishing the mount as part of `do_debug`'s attach path for a device
target, since nothing in the flow mounts anything today; (b) a pre-attach check that the
source the session will debug is the source on the host, which under a live mount is an
assertion that the mount is up and covers the target; (c) generation of absolute
`pathMappings` from the mount record, reachable both by the DAP attach request the
command sends and by the extension building a launch config.
Out of scope: the hash-diff sync engine (s4.2, unreachable under D2); the restart /
re-import loop that runs on top of the mount (s4.5); the editor-side plumbing that
forwards the generated mappings into a VS Code session (s7.1, already shipped and
waiting).

## Design constraints

- Source is live by construction under a mount, so the guard is not a hash diff: it
  asserts the mount is established and that the module the boot script will import
  resolves under it. A hash comparison against a device copy would be comparing a file
  to itself.
- Establishing the mount has to happen after `ensure_raw_repl` and before
  `exec_raw_no_follow` runs the boot script - `mount_local` needs the raw REPL for
  `__mount()`, and the import has to see `/remote` already there.
- A mounted session forces mpremote to keep reading. `SerialIntercept.read` answers
  filesystem RPC from any read, so returning after the handshake (`commands.py:1194`)
  would strand the target on its next filesystem access. Mount mode takes the
  `_stay_attached` shape the serial-DAP and `--dap-log` paths already use.
- An aborted mount leaves the board blocked in a filesystem RPC with no software
  recovery: Ctrl-C is consumed as RPC payload and the REPL never returns. Teardown must
  umount on every exit path, and the failure text has to tell the user a power cycle is
  what clears it.
- Generated pathMappings are ABSOLUTE local paths (multi-root safe) - this is an
  explicit acceptance criterion from the roadmap; never emit `${workspaceFolder}` or
  relative roots.
- The user never writes pathMappings by hand anywhere in the v1 flow.

## Approach sketch

1. Give a target a source root to mount (`mpdebug.toml` key; default the project
   directory holding the config). Absolute, resolved host-side.
2. In `do_debug`'s device path: raw REPL, mount the source root, then exec the boot
   script so the target imports from `/remote`. Umount on every exit path.
3. Build pathMappings from the mount record: `remoteRoot` is the mount point
   (`SerialTransport.fs_hook_mount`), `localRoot` the absolute source root. Unix keeps
   the identity mapping it already has.
4. Guard: fail before the boot script if the mount did not establish, or if the target
   module does not resolve under the source root - naming the file it looked for.
5. Emit the mappings in the handshake result so both consumers can reach them: the DAP
   attach request s5.3 sends, and the extension's launch config.

## Acceptance criteria and tests

- A device target debugs a file that exists only on the host: edit it, run, hit a
  breakpoint on a line that was never uploaded. Runs against the unix firmware over a
  pty in CI, and on the PYBD_SF6 in the hardware suite.
- Mount-mode session on a multi-root-style layout: breakpoints bind with the generated
  absolute mappings (no `${workspaceFolder}`, no relative paths in the wire request).
- Round-trip property: for every file under the source root,
  `_filename_as_debugger(_filename_as_debugee(local))` is identity under the generated
  mappings (drives out the prefix-swap edge cases; run against `pdb_adapter.py:204/217`).
- The mount is torn down when the session ends, including on an exception and on
  Ctrl-C - a following `mpremote exec` on the same device succeeds without a power cycle.
- Guard: a target whose module is not under the source root is refused before the boot
  script runs, naming the path it looked for, rather than failing as an ImportError from
  the device.
- Adversarial: the source root is a symlink, or the target module sits in a subpackage,
  or two targets in one config mount different roots in sequence.
