# debugpy + mpremote: carry DAP over the REPL stream on a single-UART board

Phase: EPIC-6 / STORY-6.7
Depends on: STORY-6.1 (`listen_stream` / `StreamTransport` / `SerialDapBridge`),
STORY-6.2 (the network path stays mainline and unchanged)
Written: 2026-08-10 at HEAD 7ef813f (micropython 19410568d6, micropython-lib b829073c39)

## Context

D7 (`ROADMAP.md:24`, `20260810_single-uart-dap-framing.md`) settled that the
second CDC is not the no-network path: no board enumerates a second CDC by
default, so the serial path as shipped costs a `boot.py` edit and a
re-enumeration before anything else. For a board with one UART and no network,
there is currently no way to reach a breakpoint at all. This story is that way:
interleave the DAP channel with the REPL on the one stream, the way
`mpremote mount` already interleaves its filesystem RPC.

Two things `mount` does not solve were named in the story rather than left to be
discovered:

1. DAP requests arrive from the host at arbitrary times, where every fs-hook
   exchange is device-initiated.
2. The program's own stdout shares the stream, and the marker byte is unescaped
   in it.

The story carries two dated amendments about (2), the second correcting the
first. The current position, measured on the bench PYBD_SF6 and recorded as the
third correction in `20260810_single-uart-dap-framing.md`: on stm32 with the
legacy STM USB stack the REPL *is* dupterm slot 1, so an `io.IOBase` wrapper
installed there sees every stdout byte - including tracebacks - and can swallow
them. Both escaping and diverting are therefore reachable from Python on this
board class, and the story starts in `micropython-lib` rather than in
`micropython`.

## Scope

In scope:

- A device-side multiplexer that owns the REPL stream during a debug session and
  presents two façades: a console sink installed in the dupterm slot, and a
  reader/writer stream handed to `debugpy.listen_stream()`.
- The wire framing for that stream, in both directions, sharing one demux point
  and one marker namespace with `mpremote mount`'s fs-hook.
- A host-side demux that splits the port's inbound bytes into console output and
  DAP frames, and a `PumpingProxy` over the DAP half so a client still attaches
  to plain localhost TCP.
- A new `dap_stream` spec (`"repl"`) reaching the multiplexer through the
  existing `_detect_dap_stream` seam, and the `caps` key that reports it.
- Throughput measured on the bench PYBD_SF6 and recorded, as STORY-6.1's was.
- The REPL trade-off and the port scope written into `docs/debugging.md`.

Out of scope, with where each goes:

- **`mpremote mount` running concurrently with a session on the same stream.**
  Three protocols on one wire, and the fs-hook's read side reads `sys.stdin`
  directly (`transport_serial.py:576-585`), so its payloads would have to pass
  through the same demux the DAP framing introduces. The framing here is
  designed so that this is an extension and not a rewrite - one marker
  namespace, fs-hook codes untouched, the echo rule stated below - but the
  first increment refuses `--source` on a `repl` channel with an explicit error
  rather than breaking it silently. Follow-up story, raised when this lands.
- **Ports where dupterm is genuinely additive** (rp2, esp32, a TinyUSB-stack
  stm32). Those need the C stdout hook the story's first amendment describes;
  that becomes the port-expansion step, not this ticket. This ticket must not
  claim a port it has not measured.
- **USB NCM** (`micropython/micropython#16459`, open). If it lands, an NCM board
  takes the existing network path unchanged. Not a dependency; nothing is
  scheduled against it.

## Files and anchors

Device side, `micropython-lib/python-ecosys/debugpy/`:

- `debugpy/public_api.py:80-101` - `listen_stream(reader, writer, is_connected)`
  is the entry point the multiplexer's DAP façade is handed to. Nothing
  downstream of `self.sock` changes.
- `debugpy/common/stream_transport.py:30-41` - `StreamTransport.__init__`
  registers the reader with `select.poll()` for `POLLIN` and the writer for
  `POLLOUT`. **The façade must therefore be a real stream object**: an
  `io.IOBase` subclass implementing `ioctl` for `MP_STREAM_POLL`, not a duck
  type. `poll()` is called fresh on every `recv`/`send` (line 60-127), so the
  façade's `ioctl` runs on every DAP wait and is the natural place to pump the
  demux.
- `debugpy/common/stream_transport.py:108-127` - `send()` already treats a short
  write as normal and reports the count. The façade may short-write.

Device side, launcher:

- `micropython/tools/mpremote/mpremote/mpy_launch_debugpy.py:155-179` -
  `_detect_dap_stream(spec)`. `spec` is `None` (TCP), `"board"` (second CDC), or
  a path. A new `"repl"` value returns the multiplexer's DAP façade. Failing to
  produce the requested stream raises; it must never fall back to TCP.
- `mpy_launch_debugpy.py:181-192` - `_dap_stream_liveness`. The REPL stream has
  no `isconnected`; on this channel the host leaving is visible as the port
  closing, which on a USB CDC is not an EOF either. Decide and state what stands
  in for it, or accept that this channel has no liveness signal and say so in the
  same place the second-CDC one is explained.
- `mpy_launch_debugpy.py:305-320` - the `MPDBG-READY` line. It is printed to
  stdout, which by then is the multiplexer's console sink; the host reads it
  through the demux. The handshake is the synchronisation point (see below).

Host side, `micropython/tools/mpremote/mpremote/`:

- `transport_serial.py:535-549` - `fs_hook_cmds`, codes 1..13. New codes for this
  story start at 14.
- `transport_serial.py:588-602` - `RemoteCommand.begin`: device writes
  `0x18 <code>`, waits for the host to echo `0x18`, then payload;
  `micropython.kbd_intr(-1)` for the transaction, `kbd_intr(3)` after.
- `transport_serial.py:1158-1190` - `SerialIntercept._check_input`: the host-side
  demux that already exists. On `0x18` it reads one more byte, **echoes `0x18`
  unconditionally**, then dispatches `PyboardCommand.cmd_table[c]`. The echo is
  fs-hook's handshake and must not fire for DAP frames; when the two demuxes are
  unified for mount coexistence, the echo becomes conditional on the code being
  an fs-hook one. Everything not a command is buffered as console output.
- `serial_dap.py:35-118` - `_SerialDuplex` / `SerialDapBridge`. The bridge shape
  is right and is reused; what changes is the target - not a second device node
  opened with pyserial, but the DAP half of the port mpremote already holds.
- `commands.py:742-790` - `_maybe_start_serial_dap`: the caps check
  (`serial_dap` absent is a hard error, not a fallback), `check_device`, bridge
  start, and `reported = dict(handshake, host=proxy.host, port=proxy.port)`.
  The `repl` channel reaches the same shape with a different target.
- `commands.py:844-887` - `_stay_attached`: the process must outlive the
  handshake on this channel, exactly as it does for a `--dap-log` proxy.

Firmware behaviour, stm32 legacy STM USB stack (the bench PYBD_SF6):

- `ports/stm32/usb.c:653-655` - `USB_VCP(0)` is installed in dupterm slot 1 as
  the REPL. This is why the slot is the whole stdout path on this board.
- `extmod/os_dupterm.c:231` - `os.dupterm` demands the native stream protocol;
  a plain class raises `OSError: stream operation not supported`.
- `extmod/os_dupterm.c:196-209` - **any exception out of the slot object's
  `write()` deactivates the slot.** On this board that is the entire stdout
  path, so an `OSError(EAGAIN)` from a full CDC TX buffer would silently kill
  both the console and the session. The multiplexer's `write` must not raise.
  A short count is safe: `mp_stream_write(..., MP_STREAM_RW_WRITE)` at line 198
  re-drives the remainder, and `mp_os_dupterm_tx_strn` reports the minimum.
- `ports/stm32/modos.c:44-66` + `usb.c:684-692` - installing the wrapper
  *detaches* `USB_VCP(0)` from the REPL. Two consequences, both real:
  - `usbd_cdc_interface.c:317` guards interrupt-char scanning on
    `attached_to_repl`, so **ctrl-C stops being an interrupt and becomes an
    ordinary data byte** for the length of the session. That removes an escaping
    problem and removes the user's interrupt at the same time; it is a REPL
    trade-off the story's last acceptance criterion requires to be documented.
  - the flow flag flips to `USBD_CDC_FLOWCONTROL_CTS`, which switches
    `usbd_cdc_tx_flow` (`usbd_cdc_interface.c:347-358`) from "never block,
    rolling buffer" to "write only what fits", and `pyb_usb_vcp_write`
    (`usb.c:902-911`) raises `EAGAIN` when nothing fits. Short writes and EAGAIN
    are the normal case on this path, not the exceptional one.
- `usbd_cdc_interface.c:315-325` + `mpconfigboard_common.h:362` - the RX ring is
  `MICROPY_HW_USB_CDC_RX_DATA_SIZE`, 1024 by default and 256 on some boards, and
  **on overflow it discards the rest of the packet silently**. This is obstacle
  (1) in its real form: not a stall, but dropped bytes mid-frame.
- `py/objstr.c:142-164` - `json.dumps` escapes control characters as a
  `\uXXXX` sequence, so a raw `0x18` cannot appear in a DAP payload either end
  produces. Relevant to the framing choice below, and deliberately not relied on.

## Design constraints

- **D3 stands:** the network transport is mainline. This is an added channel, not
  a replacement, and no existing path may change shape for it.
- **No silent fallback.** Requesting `repl` and not getting it is an error, the
  same rule `_detect_dap_stream` and `_maybe_start_serial_dap` already hold.
- **fs-hook's wire protocol is byte-identical after this.** Codes 1..13, the
  unconditional echo for those codes, `kbd_intr(-1)` around a transaction. A
  `mount` against a board that is not debugging must be unaffected, and the
  existing mount tests are the check.
- **The multiplexer's `write` never raises** (`os_dupterm.c:207`).
- **The host must not distinguish console from DAP by looking at content.** That
  is an acceptance criterion, and it is what rules out "scan for a `Content-Length`
  header" and "assume DAP frames are the JSON-looking ones".
- **`caps` is derived from the channel actually picked**, never guessed - the rule
  `_detect_dap_stream`'s docstring already states.
- The `docs/debugging.md` capability vocabulary is held by
  `tests/test_docs_capabilities.py` with whole-token matching. A new caps key
  must be added there in the same change or that test fails, which is the point
  of it.

## Approach sketch

**One object owning the port, two façades.** The dupterm slot's `write()` is
called with program stdout; the DAP stream's `write()` is called with DAP frames;
a single object cannot tell them apart, so the multiplexer exposes two
`io.IOBase` façades over shared state. `console` goes in dupterm slot 1;
`dap` goes to `listen_stream()`. Both need `ioctl` - the first because
`os.dupterm` demands the stream protocol, the second because `StreamTransport`
registers it with `select.poll`.

**Framing, device to host.** `0x18` keeps its meaning as "a marker follows", and
the code namespace is shared with fs-hook:

| code | meaning |
| --- | --- |
| 1..13 | fs-hook, unchanged, host echoes `0x18` |
| 14 | DAP frame: two length bytes, then that many payload bytes. No echo. |
| `0x18` | a literal `0x18` in console output |

Console output is escaped (`0x18` → `0x18 0x18`) and otherwise passes through, so
everything unmarked is console. The rule the host applies is structural - read a
marker, read a code, read a count - and never inspects a payload, which is what
criterion 3 asks for. The explicit length is chosen over reusing DAP's own
`Content-Length` header so that the demux never parses the payload at all:
`json.dumps` escaping control characters (`objstr.c:158-161`) means a raw `0x18`
cannot appear in a DAP frame today, but that is a content-level assumption about
a component this layer should not be coupled to.

**Framing, host to device.** The host writes DAP frames with the same envelope.
It needs one because the device's stdin is not exclusively DAP: the fs-hook read
path reads `sys.stdin` directly, and a future `mount` coexistence needs the same
demux on the device side. Making both directions symmetric now costs two bytes
per frame and removes a special case later.

**Flow control for obstacle (1).** The host may send a request at any time, and
the device only pumps the demux when something calls the façade's `ioctl` or
`readinto` - which under `settrace` is at each trace event, the same poll point
the network path has. The difference is that the CDC RX ring drops the tail of a
packet on overflow (`usbd_cdc_interface.c:319-322`) rather than exerting
back-pressure. So: **one DAP request in flight at a time**, host-side, and the
frame size bounded below the smallest supported ring. A `setBreakpoints` with
many breakpoints is the realistic overrunner and is what the adversarial test
should send.

**Synchronisation.** Framing must start at a point both ends agree on. The
device is unframed while `mpremote` is still driving the raw REPL to launch the
boot script, and framed from the moment the multiplexer is installed. The
`MPDBG-READY` line is the natural boundary: the device installs the multiplexer,
then prints the handshake through it as its first framed console bytes; the host
switches its reader to the demux before executing the boot script, so it reads
the handshake already framed. Verify the raw-REPL exchange that precedes it is
complete before the switch - a half-read `OK` from `exec` would be consumed by
the demux as console output.

**The stdout question, decided.** Escape rather than divert. Escaping keeps
program output going where the user expects it - mpremote's own stdout - and
costs one byte per `0x18` in the program's output, which is a byte no ordinary
program writes. Diverting into DAP `output` events would put the program's
prints in the editor's debug console, which is what a VS Code user expects, but
it silently drops output for anyone running `mpremote debug` from a terminal
without a client attached, and it makes a traceback during a session invisible
except through the DAP channel that may be the thing that is broken. The wrapper
is capable of both (measured: 33 bytes swallowed reached the host as nothing);
routing to `output` events is a later option once the channel itself is proven,
and the wrapper being the same object either way is the reason it is deferrable.

## Acceptance criteria and tests

The story's criteria, verbatim from `ROADMAP.md:1511-1521`:

- [ ] a board with one UART reaches a breakpoint over that UART, with no network
      configured and no second interface enumerated.
- [ ] a program that prints the marker byte does not desynchronise the link, and
      the test writes it deliberately.
- [ ] the host distinguishes program output from DAP frames without a heuristic
      on content.
- [ ] throughput measured on hardware and recorded, as STORY-6.1's was.
- [ ] whichever of escaping / diverting stdout is chosen, the trade-off it makes
      to the REPL during a session is stated in `docs/debugging.md`, along with
      which ports the chosen mechanism reaches.

How each is proved:

1. **Breakpoint over one UART.** A HIL test, in `tests/hil/`, run against the
   bench PYBD_SF6 booted single-VCP - which means the test must assert the board
   is in that mode rather than assume it, since the bench board's `boot.py`
   currently sets `2xVCP+MSC` and the HIL records carry that as provenance. The
   negative probe from STORY-6.1 criterion 2 is the model.
2. **Marker byte in program output.** The sample program prints
   `b"\x18"` and `b"\x18\x18"` and a byte sequence that looks like a valid DAP
   frame header (`0x18 0x0e` followed by a plausible length), then hits a
   breakpoint. All three must arrive as console output and the session must
   still work. Host-side, this is also reachable without a board: the demux is
   ordinary Python and should have unit tests feeding it adversarial byte
   streams, including a marker split across two reads.
3. **No content heuristic.** Structural: the demux takes a length and copies
   that many bytes. The test that proves it is the one in (2) - a DAP-shaped
   payload in console output that is *not* treated as DAP.
4. **Throughput.** Same measurement STORY-6.1 recorded, into the same place, with
   the framing overhead visible against the second-CDC number.
5. **Documentation.** `docs/debugging.md` gains the channel, the ctrl-C
   trade-off, and the sentence naming stm32-with-the-legacy-USB-stack as the port
   scope. `tests/test_docs_capabilities.py` holds the new caps key.

Adversarial checks beyond the criteria:

- **RX ring overflow.** Send a `setBreakpoints` large enough to exceed the ring
  while the device is between trace events. The failure being guarded against is
  silent truncation, so the test must assert the response, not the absence of an
  exception.
- **The dupterm deactivation path.** Force the console façade's write to hit a
  full TX buffer and confirm the slot survives - a test that mutating the
  `write` to let `EAGAIN` escape actually fails. Reachable on the unix port with
  a stub, and worth having there because on hardware the symptom is a board that
  has gone quiet.
- **`mount` refusal.** `--source` with a `repl` channel must fail with a message
  naming the reason, and there must be a test that it does, so the deferral is
  visible rather than a coincidence.
- **fs-hook untouched.** The existing mount tests, run unchanged.

Hardware needed: the bench PYBD_SF6 only, in single-VCP mode.

## Workflow shape

Runs inside the phase's larger workflow, with one deviation: the device-side
multiplexer and the host-side demux are one design and should be implemented by
one agent, not split, because the framing is the contract between them and a
split invites two half-compatible readings of it. The host-side unit tests over
adversarial byte streams can be written in parallel against the framing table
above before either side exists.

## Open questions

- **Liveness on this channel.** `_dap_stream_liveness` returns `isconnected` for
  a CDC; the REPL stream has one too (it is `USB_VCP(0)`), but its DTR going down
  means mpremote itself has gone, which is a different event from a DAP client
  leaving - the client here talks to mpremote's TCP proxy, not to the board. The
  proxy losing its client is probably the right signal and it is host-side, which
  would mean this channel needs no device-side liveness at all. Confirm before
  implementing, because getting it wrong leaves a board stopped at a breakpoint
  needing a power cycle, which is the exact failure `_peer_gone` exists for.
- **Whether the console façade should buffer.** Every stdout write becomes an
  escape scan plus a framed write. On a program that prints in a tight loop that
  is a lot of small CDC writes. Measure before adding a buffer, since a buffer
  adds a flush-ordering problem between console and DAP output.
- **What `caps` key names this.** `serial_dap` already means "a dedicated second
  CDC". This is also serial DAP, and a client that reads `serial_dap: true` and
  expects a second device node would be wrong. Needs a distinct key
  (`repl_dap`?), and the four-copies-of-a-vocabulary problem Q12 found says to
  decide it once and let `tests/test_docs_capabilities.py` hold it.
