# mpremote: `debug` unix flow end-to-end (ensure firmware → launch → parse handshake → attach)

Phase: EPIC-5 / STORY-5.3
Depends on: s5.1 (skeleton), s5.2 (target resolution), STORY-3.1 (manifest, done), EPIC-1 (done)
Written: 2026-07-06 at HEAD 59fab8450a (micropython 18c76f7c56, micropython-lib 0d42fcd5bc; ampremote/micropython 5b459e2d57)

## Context

The unix port is the lowest-friction proof of the whole resolve→ensure→launch→attach
model: no device, no sync, subprocess stdout as the control plane. Everything this
flow needs already exists and is test-proven in the wrapper repo — this ticket moves
the orchestration from pytest fixtures into the command. Bound by D1 (command owns
orchestration) and the handshake-only rule: the endpoint comes from the `MPDBG-READY`
line, never from config.

## Scope

In scope: `kind=unix` branch of `do_debug`: locate/ensure a debug-capable unix
binary; set `MICROPYPATH`; spawn the boot script as a subprocess; read stdout until
the `MPDBG-READY` line; report endpoint + caps (and, for now, leave the subprocess
running for an external DAP client to attach — the command IS the launcher).
`--port` passthrough (default 0 = auto).

Out of scope: acting as a DAP proxy or client itself; serial/network control planes
(s5.4/EPIC-6); firmware CI publishing (s3.2); VS Code integration (s7.1, which
spawns this command and reads the same line).

## Design constraints

- No literal ports/IPs: `--port` default 0; the reported endpoint is authoritative
  (public_api.py port-0 fallback means the handshake may differ from the request).
- The launcher's stdout is line-oriented but arrives in non-blocking chunks — parse
  by accumulating and splitting, exactly like `_read_mpdbg_ready`; do not readline()
  on a blocking pipe (the banner + prompt output precedes the handshake).
- Respect capability truth: after parsing caps, validate the target's `requires`
  list (s5.2) — mismatch is a hard error before reporting success.
- The subprocess must be cleaned up on error paths (terminate→kill ladder as in
  `debuggee.py:219-233`).

## Approach sketch

`_do_debug_unix(state, target, module, method, port)`:
1. Resolve binary: env override → target firmware → error with `make firmware-unix`
   hint.
2. Build env (`MICROPYPATH` covering project src + debugpy module path — for the
   command running outside this wrapper repo, the debugpy module location becomes a
   config/packaging question: see Open questions).
3. Spawn `[binary, launcher, module, method, str(port)]`, non-blocking stdout.
4. `_read_mpdbg_ready(proc, timeout)` → `{host, port, caps}`; validate caps against
   `requires`. NOTE: on unix `_detect_host()` (launcher `:34-54`) always reports
   `host: "0.0.0.0"` — a bind address, not a connectable one. Translate to
   `127.0.0.1` before emitting (rule owned by s5.4: the tooling never emits a raw
   `0.0.0.0` endpoint). Then print a stable one-line summary (what s7.1's extension
   parses — machine-friendly: re-emit the `MPDBG-READY` JSON with the resolved host).
5. Leave the process attached to the console (stream its output) until it exits or
   Ctrl-C; on Ctrl-C terminate the subprocess.

## Acceptance criteria and tests

- [ ] `mpremote debug unix target:main` (with `mpdebug.toml` present) reaches a
  breakpoint set by a DAP client with zero hand configuration.
- [ ] port is auto (0) end-to-end; the reported port comes from the handshake; grep
  the implementation for port literals — none besides the argparse default of 0.
- [ ] missing binary produces the build hint, not a traceback; handshake timeout
  names the expected line and dumps captured stderr.
- [ ] subprocess is reaped on every failure path (test with a binary that exits
  immediately and one that never prints the handshake).
- Adversarial: launcher printing a corrupt/duplicate `MPDBG-READY` line (must error,
  matching the "exactly one" contract tested at `test_epic1_foundations.py:51`);
  caps missing a required capability → hard error naming the capability.

## Revalidation (2026-08-06, phase entry at HEAD 77202da)

This ticket predates s5.1, s5.2, s5.4 and Q8; several of its instructions are
now either already done or actively wrong.

Anchors re-resolved (micropython `2ba7cf660087`): launcher `_parse_args` is
`:60`, `debugpy.listen()` `:96`, the handshake emit `:101`, `wait_for_client()`
`:104`; `launcher/firmware.py` is now `cmd_list :119`, `cmd_verify :171`,
`cmd_fetch :214`, plus a `cmd_select :340` the ticket never saw.

**Already built — do not re-do:**

- The handshake parser is shared, not to be ported: s5.4 landed
  `mpremote/mpdebug_handshake.py`, and both existing readers call it. s5.3
  passes `control_kind=CONTROL_KIND_UNIX` and gets the record.
- The `0.0.0.0` -> `127.0.0.1` translation the ticket asks for is that module's
  job and is done. s5.3 must not re-implement it.
- Target resolution and `requires` validation landed with s5.2.

**Wrong now:**

- "`--port` default 0 = auto" and the acceptance item "port is auto (0)
  end-to-end" are unachievable. Q8 removed `listen()`'s port-0 fallback: no
  port in this tree implements `getsockname()`, so `port=0` raises, and s5.1
  rejects `--port 0` up front with that reason. The default is `None`, meaning
  the device applies `debugpy.DEFAULT_PORT`. Read the criterion as "no port
  literal in the flow; the reported port comes from the handshake" — which
  still holds and is still worth testing.
- The note that `listen()` falls back to the default port when the runtime
  cannot report the bound port describes deleted behaviour.

**Better than the ticket assumed:** `firmware/firmware.toml` has real
`download_url`s since s3.2, so the ensure step's third option is live. The v1
order stands as written — `MPY_DEBUG_FIRMWARE`, then the target's `firmware`
entry resolved to a local build, then fetch — but fetch now works rather than
being a post-s3.2 promise, and `cmd_select --need` can resolve a capability
requirement to an artifact directly.

**Watch for:** the fixture at `tests/fixtures/debuggee.py` still asserts the
human banner line during startup; the ticket is right that the command must
not depend on it. Also note s5.4's carried-forward item — a failed run leaves
the device blocked in `wait_for_client()` with a bound socket — applies here
too: a unix subprocess that has bound its port must be reaped on every error
path, or the next run collides with it.

The MICROPYPATH/packaging open question stays open and deferred to STORY-8.2/8.3:
s4.1's `ensure_debugpy_installed` solves this for devices, not for a unix
subprocess, which still needs the path handed to it.

## Execution progress

**IN REVIEW, not landed (2026-08-06).** First implementation is on
`mpremote_debug_unix` (submodule, off `mpremote_debug_handshake`) with tests
uncommitted in the top-repo working tree. The composition is NOT moved and
`main` is unaffected. The review returned 8 mustFix; the fix round hit a
session limit before running, so the findings stand. Full text saved to
`planning/.s5.3-open-findings.json` (scratch dirs rotate between sessions and
have already eaten one findings file this week).

The blocking ones, worth summarising because two are integrity problems
rather than bugs:

- **The success path orphans the child.** `_do_debug_unix` returns straight
  after the handshake, so mpremote exits while the micropython process sits in
  `wait_for_client()` holding the port — verified by pid and `ss -ltnp`, and
  the next run then collides with it. The ticket's approach sketch step 5 says
  to stay attached until the child exits or Ctrl-C; the implementation skipped
  that.
- **The test harness hides exactly that defect**: it `pkill`s
  `micropython.*mpy_launch_debugpy` before every invocation, with a docstring
  admitting tests leave processes running. Running the happy-path test alone
  leaves a live process on its port.
- **Three tests have `pass` bodies and assert nothing**, while their names
  claim the ticket's adversarial items (duplicate MPDBG-READY, missing
  required capability, reaping on missing binary).
- The "reported port comes from the handshake" criterion is not tested — both
  port tests compare against the port they requested, proved by a mutation
  that hardcodes the requested port and still passes.
- `import fcntl` at the top of `commands.py` breaks every mpremote command on
  Windows, which upstream supports.
- `_unix_env()` overwrites `MICROPYPATH` wholesale, so debugpy installed the
  documented way (`~/.micropython/lib`, where s4.1's installer and mip put it)
  stops being importable.
- An exception between spawn and the reaping ladder leaks the child and the
  temp dir; only `HandshakeError`/`KeyboardInterrupt` are caught.
- The branch leaves the top-repo suite red: two s5.2 tests still assert the
  removed "not supported yet" strings.
