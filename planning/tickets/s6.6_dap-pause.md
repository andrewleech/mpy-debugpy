# debugpy: make the DAP `pause` request stop the target

Phase: EPIC-6 / STORY-6.6
Depends on: EPIC-1 (protocol correctness), STORY-4.5 (which found this)
Written: 2026-08-10 at HEAD `cfef4d6ed3` (micropython `4eaafbc5bc`, micropython-lib `1eb7c82bfd`)

## Context

Found on 2026-08-09 while closing STORY-4.5 and filed as a risk-register row
rather than fixed in passing. `_handle_pause` answers the request with success
and sets `paused`, and no stop decision reads it: the client's UI goes to the
stopped state while the program keeps running. Every subsequent request the
client makes on that belief - `stackTrace`, `scopes`, `variables` - is answered
from `current_frame`, whatever frame the target happened to be in when the last
trace event fired, so the user is shown a frame the program has already left.

The row's second half is why it is a story: none of the existing tests can
catch this, because every one of them drives a target that stops on its own at
a breakpoint. A target that never stops has to be written before the assertion
can exist.

This story sits in EPIC-6 next to STORY-6.5 for the same reason: both are
debug-session capabilities in the debugpy server rather than transports, and
EPIC-1 is closed.

## Scope

In scope: consuming a pending pause in the stop decision, reporting the stop
with reason `pause`, removing the write-only state that made the request read
as implemented, and a host-side scenario that pauses a free-running target and
proves it is stopped rather than merely reported stopped.

Out of scope: pausing a target that is not executing traced bytecode (blocked
in `time.sleep`, in a C-level loop, or between runs of a `--loop` session).
There is no trace event to stop on there, and no mechanism in this design that
could produce one; the request stays pending and takes effect at the next line.
Documented, not fixed. Also out of scope: a HIL scenario, which the host suite
does not need to prove the mechanism.

## Design constraints

- `DebugSession.paused` is written in five places and read in none;
  `DebugSession.stepping` is written in six and read once, by the reason
  ladder. Duplicated state that only looks like a mechanism is what hid this
  defect, so the fix must not leave a second copy behind.
- The stop reason must be derived by whichever code made the stop decision.
  `should_stop` knows which of the three reasons applied; the session does not.
- `should_stop` is the hot path, called for every trace event. No debug
  printing, no allocation.
- A pause consumed at a `call` event would report the `def` line before the
  body has run, and at a `return` event a frame that has already produced its
  value - the same distinction `should_stop`'s breakpoint check already makes.
  Only `line` is a place a user asked to be stopped at.
- The device-side code is upstream-bound (`micropython-lib` PR #1022) and must
  stay MicroPython-compatible: no f-strings in the hot path, no CPython-only
  attributes.

## Approach sketch

`should_stop` gains a `hit_pause` flag alongside `hit_breakpoint`, cleared at
entry and set when a pending `paused` is consumed on a `line` event. The
consumption clears `paused` and any pending `step_mode`, since a pause is a
user interrupt and a step that survived it would fire later at a point nobody
asked for.

The reason ladder moves off `DebugSession.stepping` and onto the adapter:
breakpoint, else pause, else step. That is exhaustive - `should_stop` returns
True for exactly those three - which is what lets both `DebugSession.paused`
and `DebugSession.stepping` be deleted rather than left write-only.

`wait_for_continue` clears `paused` on the way out, so a `pause` that arrives
while the target is already stopped is dropped instead of stopping it again one
line after the user's next `continue`.

## Acceptance criteria and tests

- [ ] A free-running target with no breakpoints set, sent `pause`, produces a
  `stopped` event with `reason == "pause"`.
- [ ] The target is *stopped*, not merely reported stopped: a value the loop
  advances every iteration reads the same twice across a real-time gap.
- [ ] `stackTrace` at that stop names the function the loop is in.
- [ ] `continue` resumes it and the target runs to completion, exit code 0.
- [ ] A `pause` sent while the target is stopped at a breakpoint does not
  produce a second stop after the following `continue`.
- [ ] Mutation check: reverting the `should_stop` consumption makes the first
  criterion fail, and reverting the `wait_for_continue` clear makes the last
  one fail.
- [ ] `make test` and `make lint` green; `make lint-submodules` green for the
  micropython-lib change.

No hardware needed: the mechanism is in the device-side server and is identical
over any transport.
