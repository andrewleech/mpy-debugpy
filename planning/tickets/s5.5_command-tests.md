# tests: drive `mpremote debug` end-to-end (unix + QEMU PTY) through the DAP harness

Phase: EPIC-5 / STORY-5.5
Depends on: s5.3 (unix flow), s5.4 (handshake plumbing); QEMU leg additionally on mpremote PR #18327 being in the tree under test (see constraints)
Written: 2026-07-06 at HEAD 59fab8450a (micropython 18c76f7c56, micropython-lib 0d42fcd5bc; ampremote/micropython 5b459e2d57)

## Context

EPIC-1 proved the harness pattern: a fake VS Code DAP client drives a real session
against a real MicroPython process, so tests fail on behaviour regressions, not
source-string drift (repo CLAUDE.md test rule). This ticket points that same harness
at the `mpremote debug` command instead of spawning the launcher directly — proving
the command end-to-end: attach, breakpoint, step, inspect, continue, with all
endpoints handshake-derived.

## Scope

In scope: pytest coverage where the debuggee is started via `mpremote debug unix ...`
(the command under test, invoked as a subprocess); a QEMU PTY leg where feasible in
CI without hardware; assertions that no endpoint is hardcoded (the test reads the
command's re-emitted handshake and attaches to THAT).

Out of scope: hardware-in-loop device tests (STORY-6.4/s6.4); mpremote's own shell
tests in `tools/mpremote/tests/` (s5.1 covers registering one there); extension
smoke tests (s7.4).

## Design constraints

- Tests stay machine-independent: no absolute paths (repo CLAUDE.md); derive paths
  from `pytestconfig.rootpath` as `debuggee.py:91` does; `mpdebug.toml` for the test
  written to `tmp_path`, not committed at repo root.
- **QEMU PTY dependency is NOT in this repo's tree**: PR #18327 (PTY detection,
  `transport_serial.py:108-111` in ampremote's tree) exists only in
  `~/ampremote/micropython`; this repo's micropython submodule @ 18c76f7c has plain
  upstream mpremote. The QEMU leg therefore requires either registering that branch
  into the `mpy-debugpy` integration branch first (recommended, Q1/D5-consistent —
  surface as a work item at phase entry) or running against ampremote. Do not let
  the QEMU leg silently test a different mpremote than the unix leg.
- The mpremote under test must be the integration's copy
  (`micropython/tools/mpremote`), invoked hermetically (e.g. `uv run --with-editable
  micropython/tools/mpremote -m mpremote ...` or PYTHONPATH), not whatever
  `mpremote` is on PATH.
- CI budget: the unix leg runs in `make test`; the QEMU leg may be marked/skipped
  when QEMU or the PTY-capable mpremote is absent — skip with a reason string, never
  xfail-mask a real failure (lesson recorded from the EPIC-1 xfail misdiagnosis).

## Approach sketch

1. `mpremote_debuggee` fixture: write `mpdebug.toml` (unix target, firmware path
   from `MPY_DEBUG_FIRMWARE` or the standard build) into `tmp_path`; spawn
   `python -m mpremote debug unix target:main` with cwd=`tmp_path`,
   `MICROPYPATH` per `debuggee.py:108`; non-blocking stdout; parse the command's
   re-emitted `MPDBG-READY` (s5.3 contract) for host/port.
2. Attach `ThreadedServer` to that endpoint; run the EPIC-1 assertion sequence:
   setBreakpoints → configurationDone → stopped(breakpoint) → stackTrace → scopes →
   variables → continue → target completes.
3. Endpoint-hygiene test: run with `--port 0` twice concurrently; both sessions get
   distinct handshake-derived ports; assert neither test nor command output contains
   a configured endpoint.
4. QEMU leg (gated): same flow with a `kind=serial` target whose connect string is
   the QEMU PTY; requires the PTY-capable mpremote (see constraints).

## Acceptance criteria and tests

- [ ] unix flow passes in CI via `make test`: attach, breakpoint stop, step, locals
  inspect (readOnly hint per caps), continue to completion — all through
  `mpremote debug`.
- [ ] endpoints asserted handshake-derived: port requested as 0, attached port taken
  from the command's output; two concurrent sessions don't collide.
- [ ] QEMU leg passes where its prerequisites exist, and skips (with reason) where
  they don't; the skip reason names the missing prerequisite.
- Adversarial: kill the debuggee mid-session — the command exits non-zero with a
  clear message and the test asserts no orphan processes; corrupt `mpdebug.toml` →
  resolver error surfaces through the command's exit code/stderr.

## Revalidation (2026-08-06, phase entry at HEAD 3bb9fb9)

Anchors re-resolved (micropython `b874d8854419`): `micropython_debuggee` is
`tests/fixtures/debuggee.py:98`, `read_mpdbg_ready` `:263`, `wait_for_msg`
`tests/helpers.py:36`, `set_breakpoints` `:62`.

**The QEMU prerequisite is already satisfied.** The ticket says PR #18327's
PTY detection "exists only in `~/ampremote/micropython`" and must be
registered first. It is in the composition today, carried transitively by
#18436's branch (`e1f8f204b6`, "Add PTY device detection for QEMU"), and
`transport_serial.py:108` uses it — s5.1 and s5.4 already depend on
`is_pty`. So no branch registration is needed and the QEMU leg cannot
silently test a different mpremote. `qemu-system-arm` is not installed on
this machine, so that leg will skip; the skip must name the missing binary.

**The auto-port criterion is dead, and its purpose with it.** "port requested
as 0, attached port taken from the command's output" and "two concurrent
sessions don't collide" both assumed `--port 0`. Q8 removed `listen()`'s
port-0 fallback and s5.1 rejects `--port 0`, because no port in this tree
implements `getsockname()`. With `--port` omitted the device applies
`debugpy.DEFAULT_PORT` — the same port every time — so two concurrent
sessions collide by construction. Keep the handshake-derived half (attach to
what the command reported, never to a configured value; that is testable and
valuable) and give concurrent sessions explicit distinct ports. Record the
collision limitation rather than papering over it: it disappears only if some
port gains `getsockname()`, which is also what would revive Q8's sub-decision.

**Partly built already.** s5.3 added
`test_unix_flow_client_can_connect_to_reported_endpoint`, which spawns
`mpremote debug`, parses the re-emitted handshake and completes a DAP
`initialize` against it. That is step 1-2 of the approach sketch as far as
attach. What is missing, and is this ticket's real content, is the assertion
sequence beyond attach: breakpoint stop, step, locals inspect with the
readOnly hint, continue to completion.

**The flake fix recorded for this story is wrong as written** — see the risk
register. "Have `wait_for_msg` return the matched message instead of
`rcv_messages[-1]`" was tried on 2026-08-05 and measured worse (3 clean of 6
against 4 of 6 unchanged), because scanning the list returns a stale match
left by an earlier request and the wait stops early. A correct fix needs a
watermark taken at entry so only messages arriving after the call count.
That is harness surgery and belongs here, but budget for it as such.

Also carried in from s5.3: `_report_debug_result` needed `flush=True` for a
pipe reader to see the endpoint before the session ends. Check the serial
path for the same problem while the harness is open.

**Correction (2026-08-06, after triage): the xfail claim below was wrong.**
The parked branch contains no `xfail` markers at all — that note came from
the test agent's summary ("2 XFAILED") and was recorded without checking the
branch. The second false agent report of the day, and the second one relayed
onward before verification.

**Triage settled the blocker: there is no product bug.** A breakpoint DOES
fire when the debuggee is started via `mpremote debug` with a unix target;
the same client sequence produces an identical
`stopped`/`breakpoint` event on the direct and mpremote paths, with
`setBreakpoints` returning `verified: true`. STORY-5.3's acceptance holds.
The parked test failed with `AttributeError: 'bool' object has no attribute
'body'` — it assigned `wait_for_msg`'s return value and dereferenced `.body`
— which was read as "the target never ran".

That exposed something worse than the blocker. `wait_for_msg` returned
`len(rcv_messages) >= count` with `count` defaulting to 0, i.e. **True
unconditionally, including on timeout**, so all nine `assert wait_for_msg(...)`
call sites in the suite asserted nothing. Fixed in `339192a`: it returns the
matched message or None, the assertions are now real, and the suite passes
with them enforced. One newly-real assertion failed immediately — the
`initialize` response is not the most recent message by the time it is
checked, because `initialized` follows it — and that test now scans instead
of requiring recency.

Remaining for this story: adopt the returned message in the parked tests
(the `.body` misuse appears at WIP lines 202, 216-217, 223-225, 232-234,
245-248, 269-270, 277-278, 361) and land them. The order-insensitive
matching question stays open and separate.

**Superseded note — the tests were said to xfail the story's own criteria.** Breakpoint stop, locals
inspect and continue — the content this ticket exists for — are marked
xfail, attributed to the target never executing when launched through
mpremote. The ticket forbids xfail-masking a real failure, so this cannot
land as-is, and the claim is UNVERIFIED. An orchestrator probe confirmed the

Resolve that first, because the two outcomes are very different: if the
