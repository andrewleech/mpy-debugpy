# mpremote: named-target model (`mpdebug.toml`) and target resolution

Phase: EPIC-5 / STORY-5.2
Depends on: s5.1 (command skeleton), STORY-3.3 (real variant set — capability names)
Written: 2026-07-06 at HEAD 59fab8450a (micropython 18c76f7c56, micropython-lib 0d42fcd5bc; ampremote/micropython 5b459e2d57)

## Context

Today's friction is config scatter: nine `launch.json` attach configs with hardcoded
IPs, an `MP_DEBUG_VARIANT` env var, and per-transport launcher invocations (ROADMAP
"The current friction"). The named-target model replaces all of it: a project-level
`mpdebug.toml` maps a target name to `kind = unix | serial | network`, a connect
string, and a capability requirement; `mpremote debug <name>` resolves the rest.
Bound by D1 (CLI owns orchestration), D4 (capability from the runtime probe, never
from names), and the global rule that serial devices are referenced by stable
`/dev/serial/by-id/<name>` paths because raw `/dev/ttyACMx` nodes renumber.

## Scope

In scope: the `mpdebug.toml` schema; a resolver that turns a target name into
(transport kind, connect string / binary path, firmware requirement, target
module:method defaults); discovery of the config file (cwd upward, like git); clear
errors for missing file / unknown name / ambiguous target; `mpremote debug` with no
target listing the available names.

Out of scope: acting on the resolution (s5.3 unix, EPIC-6 device flows); firmware
fetch/build itself (`launcher/firmware.py`, STORY-3.x); VS Code target picker
(STORY-7.2 reads the same file — schema changes after 7.2 starts need coordination).

## Design constraints

- Serial connect strings in examples and docs use `/dev/serial/by-id/...` (stable
  across replug); accept any pyserial-valid device but warn on `/dev/tty*` paths.
- A target's `requires` (capability list) is checked against the RUNTIME probe from
  the `MPDBG-READY` caps dict after launch — a mismatch between required and probed
  capability is a hard error (STORY-3.3 acceptance), not a warning.
- No IP addresses or ports in `mpdebug.toml` for network targets: the device reports
  its own endpoint via the handshake (design position). A network target names the
  serial control-plane device (for the pre-IP handshake) or relies on default
  connect; it never names the debug endpoint.
- Errors are `CommandError` with actionable text (mpremote's existing error type in
  `commands.py`), never tracebacks.

## Approach sketch

Schema (draft to refine during implementation):

```toml
[target.unix]
kind = "unix"
firmware = "unix-settrace-localnames"   # firmware.toml variant id or "system"
program = "target:main"                  # default module:method

[target.pico]
kind = "serial"
device = "/dev/serial/by-id/usb-MicroPython_Board_in_FS_mode_XXXX-if00"
requires = ["settrace", "save_names"]

[target.esp32]
kind = "network"
device = "/dev/serial/by-id/usb-Espressif_USB_JTAG..."  # control plane only
requires = ["settrace"]
```

Resolver: `_resolve_target(name) -> Target` dataclass-like record; search
`mpdebug.toml` from cwd upward; no name given + exactly one target → use it; no name
+ several → `CommandError` listing names ("ambiguous target; choose one of: ...");
unknown name → error listing names. Keep parsing tolerant of unknown keys (forward
compatibility with s7.2's picker metadata).

## Acceptance criteria and tests

- [ ] a named target resolves to transport kind + connect string + firmware
  requirement; `program` default flows through to the launcher argv.
- [ ] serial connect strings using `/dev/serial/by-id/...` pass through untouched;
  a `/dev/ttyUSB0`-style path resolves but warns.
- [ ] absent config, unknown name, and ambiguous no-name cases each produce a
  one-line actionable `CommandError` (test asserts message content, not type only).
- [ ] `requires` capabilities are validated against the probe keys list; an unknown
  capability name in the file is an error at resolve time (catches typos before a
  device is touched).
- Adversarial: duplicate target names in the file; `kind` outside the enum; an
  `mpdebug.toml` in a parent directory being silently preferred over a local one
  (must pick nearest); empty file.

## Revalidation (2026-08-05, phase entry at HEAD 77a22b1)

Anchors re-resolved on the current composition (micropython `60d32aa0a736`):
`load_user_config` is now `main.py:484`, `do_connect` is `commands.py:23`
(signature unchanged from upstream — s5.1 deliberately left it alone), and the
probe-key assertion is `tests/test_epic1_foundations.py:38`. The capability
vocabulary is unchanged: `settrace`, `save_names`, `set_local`, `f_back`, and
it is mirrored in `launcher/firmware.py:55` `KNOWN_CAPABILITIES` — validate
`requires` against that single list (per the roadmap-review note), not against
a hand-copied set.

**One assumption in this ticket is wrong.** It states "tomllib is stdlib from
Python 3.11; mpremote's floor allows it". mpremote declares
`requires-python = ">=3.4"` (`tools/mpremote/pyproject.toml:30`), has no toml
import anywhere today, and no toml dependency — its only config precedent is
`load_user_config`, which `exec`s a Python file. So a bare `import tomllib`
would break the declared floor, and adding `tomli` as a hard dependency makes
every mpremote user carry it for a debug-only feature, which an upstream
reviewer would reasonably push back on.

Decided: import lazily inside the resolver — try `tomllib`, fall back to
`tomli`, and if neither is importable raise a `CommandError` naming both.
No new hard dependency, no import cost for the other commands, and an
actionable message rather than a traceback on an old interpreter. (The
declared 3.4 floor is itself stale — mpremote uses f-strings throughout — but
correcting it is upstream's call, not this ticket's.)

Also settled from s5.1 as executed: `target` currently accepts `"unix"` (which
errors as not-yet-implemented) or a connect string, and `program` defaults
device-side rather than host-side. s5.2 replaces the former with resolution
and should keep the latter, since the device applies its own default when the
argv element is omitted.

## Execution progress

**COMPLETE (2026-08-05, commit 505ac27).** `mpremote_debug_targets` (one commit
on top of `mpremote_debug_command`) registered in `mbm.toml`; pin
`60d32aa0a736` -> `38a903b8de20`. Schema is `[target.<name>]` tables with
`kind` (unix|serial|network), `device`, `firmware`, `program`, `requires`;
unknown keys are ignored for s7.2's picker metadata. Discovery walks cwd
upward, nearest file wins, stopping at a `.git` boundary or `$HOME` so a stray
config outside the project is never picked up. 71 tests across s5.1+s5.2;
suite 197 passed / 1 xfailed.

The review's blocking finding was a design one, not a missing case: deciding
whether the positional was a target name or a connect string by SHAPE. The
regex accepted paths, `id:`/`port:` prefixes and the `a0`/`u1`/`c1`
shortcuts, but not a bare `COM4` — a documented mpremote connect device — so
on Windows every bare COM invocation became "unknown target" as soon as any
`mpdebug.toml` was discoverable. The heuristic is gone: a name either matches
a configured target or is handed to the transport, which is what `do_connect`
already accepts. A mistyped name therefore fails as a device, and
`target_hint()` appends the configured target names to that error — verified
through the CLI for both `COM4` and a typo.

Decided during revalidation and unchanged: TOML is imported lazily inside the
resolver (`tomllib`, then `tomli`, else a `CommandError` naming both), because
mpremote declares `requires-python >=3.4` and carries no toml dependency.

The third copy of the capability vocabulary is accepted rather than removed —
an upstreamable mpremote module cannot import the wrapper's `launcher/` — but
the drift is now guarded: the EPIC-1 handshake test pins the LIVE probe keys
against `launcher/firmware.py`'s `KNOWN_CAPABILITIES`, and a further test pins
all three copies equal.

Carried forward, not blocking: whole-file validation means one bad `[target.*]`
entry aborts any debug invocation in that project (fail-fast, but coupling
unrelated targets); `mpremote debug app:run` reads `app:run` as the target
since argparse fills `target` first, so relying on implicit resolution while
naming a program needs `mpremote debug auto app:run`, which is undocumented;
and `firmware` is stored opaquely, with nothing consuming it until s5.3.
