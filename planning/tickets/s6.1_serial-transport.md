# mpremote: serial device transport — localhost↔serial DAP bridge for multi-CDC boards

Phase: EPIC-6 / STORY-6.1

Revalidated: 2026-08-08 at HEAD 28591b41cc (micropython 2c816215dc, micropython-lib 5d4b78dd39) -

## Context

SPIKE-2.2 (`../SPIKE-2.2-serial-dap.md`) found DAP-over-serial is board-dependent:
clean on boards exposing a second USB CDC interface (native-USB: RP2040, ESP32-S2/S3,
some STM32/nRF52), high-risk on single-UART boards (CP2102/CH340 bridge boards —
most classic ESP32 devkits). Decisions binding this ticket:

- **D3 (2026-07-05):** serial DAP is first-class only on multi-CDC boards; network is
  the primary device transport.
- **Q3 DECIDED (2026-07-06):** v1 ships network-only for single-UART boards. The
  single-UART framing/escaping work is *retained but deferred* — see the appendix,
  which preserves the spike's design detail so a later follow-up spike starts warm.

So this ticket builds the serial path **only for the multi-CDC subset**, gated on a
runtime probe (never inferred from a board name — same philosophy as STORY-1.2 /
`caps` in the MPDBG-READY handshake).

## Scope

In scope:
- A device-side stream adapter (`StreamTransport`, sketch below) letting the debugpy
  server run its DAP channel over a second CDC interface instead of a TCP socket.
- A host-side localhost↔serial DAP bridge owned by `mpremote debug`: VS Code attaches
  to a localhost TCP port; the bridge shuttles bytes to/from the dedicated CDC
  interface.
- A runtime probe for "does this board expose a second CDC interface routed to DAP",
  surfaced in the handshake `caps` (e.g. `serial_dap: true/false`).

Out of scope (deferred, with detail retained in the appendix):
- Single-UART framing/escaping (mux DAP with REPL/stdout on one stream) — future
  follow-up spike, per Q3.
- Any change to `messaging.py` framing (Content-Length + JSON stays as-is; the spike
  confirmed only the byte-stream source needs to change).

## Files and anchors

Verified at the stamped SHAs:

- **What the server assumes of "the socket"** (the adapter must match all of it):
  `micropython-lib/python-ecosys/debugpy/debugpy/common/messaging.py` —
  `self.sock = sock` (:11), `send(header+content)` (:51), `recv(...)`
  (:93/:114/:144, must raise `OSError` errno 11/35 for no-data and return `b""` on
  close), `close()` (:179). `settimeout` is mutated at runtime from OUTSIDE the
  channel: `public_api.py:62` (0.001 after initialize) and multiple sites in
  `debugpy/server/debug_session.py` (0.001/0.5/1.0/None at protocol points). The
  adapter must be socket-shaped including the settimeout state machine.
- **Trace-callback frequency constraint:** `debug_session.py` trace function calls
  `process_pending_messages()` on every call/line/return event; paused busy-poll is
  ~10 ms (`pdb_adapter.py` wait_for_continue). `recv()` must be cheap
  (`select.poll(0)` + readinto).
- **Non-blocking-poll precedent on device:** mount's `fs_hook_code` in this repo's
  mpremote — `micropython/tools/mpremote/mpremote/transport_serial.py:440` (code
  string), `mount_local` (:319) — proves `select.poll` on a stream works mid-execution.
- **Reconnect/rfc2217 primitives are NOT in this repo's mpremote** (plain upstream at
  18c76f7c56): no reconnect or rfc2217 code exists under
  `micropython/tools/mpremote/`. They live only in ampremote (5b459e2d57):
  `mpremote/commands.py:80` (`do_reconnect`), `mpremote/main.py:548-559` (reconnect
  config/env default), `mpremote/repl.py:6` (`_is_rfc2217`). Per Q1, `do_debug`
  develops on a branch consumed by BOTH trees — so this ticket must treat reconnect
  as an *optional* integration (feature-detect, don't hard-depend), or the branch
  won't apply to upstream master. Board-reset handling can use ampremote's reconnect
  when present and degrade to a clear error upstream.

## Design constraints

- No background thread on the device (server is trace-callback-driven) — the adapter
  is polled, never threaded, on-device. The HOST bridge may thread freely (CPython).
- Capability truth: `serial_dap` reported by runtime probe in `caps`; a board without
  a second CDC never advertises it. Mismatch between claim and probe is a hard error
  (STORY-3.3 rule).
- Serial device references use `/dev/serial/by-id/<name>`, never raw `/dev/ttyACMx`.
- Upstream-mergeable: device-side adapter lands in micropython-lib debugpy; bridge
  lands in the mpremote `debug` command branch (Q1: one branch, two consumers).

## Approach sketch

1. Device side: implement `StreamTransport` per the spike's sketch —
   `recv(n)`/`send(data)`/`settimeout(s)`/`close()` over reader/writer stream objects
   with `select.poll`; `debugpy.listen()` grows a way to accept a pre-existing stream
   pair instead of binding TCP (keep the TCP path untouched).
2. Probe: at boot-script time, detect a usable second CDC interface (port-specific;
   start with RP2040 `machine.USBDevice` / rp2 TinyUSB CDC #2) and report
   `serial_dap` in `caps`.
3. Host side: `mpremote debug` opens the second CDC device node (by-id, second
   interface suffix), binds a localhost listener, and pumps bytes both ways;
   endpoint goes into the same MPDBG-READY-derived attach flow as TCP (s5.4's
   control/data-plane split — control plane stays on the primary REPL channel).
4. First target: **rpi_pico_w** (native USB, in the Q2 board set). PYBD_SF6 (STM32
   multi-CDC, `MICROPY_HW_USB_CDC_NUM`) second. ESP32_GENERIC is single-UART —
   explicitly network-only in v1.

## Appendix — retained single-UART framing detail (deferred by Q3, do not lose)

From SPIKE-2.2 §2, preserved for the future follow-up spike:

- One shared byte stream ⇒ DAP frames need collision-proof framing against arbitrary
  program output. Mount's `0x18` sentinel scheme is device-initiated, half-duplex,
  Ctrl-C-disabled and desync-tolerant only because fs-RPC is rare/short; DAP would
  run a scanner permanently, host-initiated, full-session.
- Escaping must cover ALL device output paths; C-level tracebacks/panic dumps bypass
  any Python `sys.stdout` wrapper and can corrupt a frame; `recv_message` trusts
  Content-Length and does not resynchronise on garbage — a resync strategy
  (SLIP/COBS-style framing with a magic delimiter) is mandatory, not optional.
- Poll cost at trace-callback frequency is proven feasible by mount's
  `RemoteCommand` poll shape; the unproven part is coexistence with unconstrained
  `print()` at 115200–921600 baud without byte loss.
- Unix-pipe prototyping validates only the socket→stream adapter (§1), not the
  multiplexing problem — do not present it as evidence for single-UART viability.

## Revalidation (2026-08-07, phase entry at HEAD 7b5b595)

**Three of the five acceptance criteria are reachable without a board, not
one.** The earlier reading (only the loopback-PTY pump test is hardware-free)
underestimated what the unix port can stand in for. Measured, not assumed:

- The unix firmware opens a second pty as a stream, registers it with
  `select.poll`, and exchanges bytes both ways
  (`open(dev,'r+b')` + `poll.register`; verified directly). So a pty is a
  faithful stand-in for the second CDC interface across the whole DAP byte
  path — the device half of this ticket can be run for real, not mocked.
- The suite already stands the unix firmware behind a pty and drives
  `mpremote debug` against it end to end (s5.5's pty leg, s6.3's pty+network
  leg), so the host-side bridge has an existing harness shape to plug into.
- `messaging.py`'s coupling to the socket is exactly `send`, `recv`, `close`
  on `self.sock`, plus `settimeout` mutated from `public_api.py` and
  `debug_session.py`. The adapter surface is four methods, as the anchors
  above already say.

So: build the `StreamTransport` adapter, the host-side bridge, and the probe,
and exercise them over a pty pair. **What still needs hardware, and must not
be quietly redefined into something a pty satisfies:** criterion 1 (a real
second CDC on rpi_pico_w enumerates and routes DAP) and criterion 2 (the
negative probe on a single-UART ESP32_GENERIC falls through to network). Those
two stay open and marked until a bench is available; criteria 3 (bridge killed
mid-session), 4's upstream half (no reconnect present -> clear error) and 5
(pump unit tests) are all reachable now.

Also ruled out as stand-ins, so nobody re-tries them: `qemu-system-arm` is not
installed here and `ports/qemu` uses semihosting console I/O rather than a
UART a pty could sit behind; and `mpremote mount` against a pty-backed unix
firmware fails with "timeout waiting for first EOF reception", which is what
keeps STORY-4.5 hardware-gated.

The reconnect/rfc2217 note in the anchors is now partly stale in one
direction: `mpremote_debug` and `mpremote_debugpy_install` are registered in
ampremote's `mbm.toml` as of STORY-8.1, so the branch is composed against
ampremote's reconnect in that tree while still applying to plain upstream.
Feature-detect as the ticket says; the composition now proves both sides.

## Hardware-free portion done (2026-08-07); ticket stays OPEN

Delivered: `StreamTransport` (micropython-lib debugpy) — a socket-shaped,
polled, thread-free adapter running the DAP channel over a reader/writer pair,
plus `listen_stream()`; and `serial_dap.py` (mpremote) — the localhost↔serial
bridge, built by generalising `dap_log.DapProxy` into a `PumpingProxy` base
rather than writing a second pump, so `--dap-log` keeps working alongside it.
Criteria 3, 4's upstream half and 5 pass. `make lint` clean, 302 tests pass.

**Criteria 1 and 2 remain open and untouched.** Neither has been ticked,
weakened, or redefined into something a pty satisfies.

Three things a reader must not mistake for finished:

- **The production path cannot activate.** `DebugSession._probe_serial_dap()`
  and the boot script's `_detect_dap_stream()` both return "no" in lockstep and
  say so, because the board-specific second-CDC detection is exactly what needs
  hardware. So `caps.serial_dap` is always false, no shipped code reaches
  `listen_stream()`, and the end-to-end test drives the real `do_debug` with a
  substituted boot script. The two halves are proven separately and meet only
  in the test. Closing that without hardware is possible — let
  `_detect_dap_stream()` accept an explicit device path (the unix port has no
  USB to detect, and mpremote already knows `dap_device`), and let
  `serial_dap` report "this session's channel IS a stream" rather than "this
  board has a spare CDC", which also fixes the ordering awkwardness of a
  capability that is only knowable after the device has already chosen. Not
  done here: it changes device-side public behaviour on a branch that is live
  in upstream PR #1022, and deserves its own pass.
- **Throughput on a real board is unmeasured and may be the thing that sinks
  serial DAP.** `recv()` reads ONE BYTE per iteration, re-polling between
  bytes, because MicroPython's `.read()`/`.readinto()` loop internally until
  full (`py/stream.c`'s `mp_stream_rw`) and a plain POSIX file — the pty
  stand-in — genuinely blocks on the second internal read. Measured on desktop
  x86: 33.7 ms and 532 KB of allocation for 4095 bytes. A device stream that
  returns short without blocking wants a chunked read instead, and that is the
  correct code for real hardware; the byte-at-a-time loop is a workaround for
  the stand-in. Validating the chunked path needs a board, and getting it wrong
  reintroduces the deadlock class of `20260806_stopped-event-flake.md`. A
  `variables` response of a few KB on a Pico could take seconds.
- **Criterion 4's ampremote half is not implemented.** The reconnect branch was
  removed rather than guessed at: `do_reconnect`'s real signature in
  `~/ampremote` matches neither the shipped call nor the reviewer's guess, and a
  wrong call is worse than the honest upstream-only error this run is scoped to.

Review found two tests that passed while asserting nothing (the `b""`-on-EOF
contract and the settimeout state machine both had no test), and criterion 3
was initially reported as delivered while `wait_for_continue()` still spun
forever on a dead channel — it now drops `sys.settrace` and exits, verified by
un-xfailing the test rather than by mutation alone.

## Wiring gap: partly closed (2026-08-08)

The shipped boot script now runs DAP over a named stream: `_detect_dap_stream()`
opens a `dap_device` path when given one, and `caps["serial_dap"]` reports which
channel was actually chosen rather than guessing at the board — which also
removes the ordering wart, since the capability was only ever knowable after the
device had already picked. `test_s6_1_stream_transport.py` drives the shipped
script instead of a stand-in fixture, which is now deleted.

Both directions of the lockstep are enforced by tests, because review showed one
direction alone is worthless: hardcoding `serial_dap: True` passed the entire
suite. The stream case asserts true, `test_epic1_mpdbg_ready_handshake` asserts
false on TCP, and both were confirmed by mutation.

**What was tried and reverted, deliberately.** Forwarding `dap_device` from
`mpremote debug`'s unix flow into the boot script's argv made the two halves meet
through shipped code, but it created a user-facing path with no way to attach:
a unix target with `dap_device` reported `host="serial", port=0`, which the
extension's handshake parser correctly rejects, and with `--dap-log` it built a
proxy to `("serial", 0)` that hangs the first client. `mpremote` has no host-side
bridge for that case and cannot easily have one — a pty's two ends are not two
independently-openable nodes the way a board's second CDC is, verified directly.
Reviewers also noted the replacement test leaned on test-only infrastructure to
supply the missing half, so the substitution had moved rather than gone.
Trading a documented limitation for a broken shipped path is a bad trade; the
mpremote side is unchanged.

So the honest position is unchanged in substance: the DEVICE half of the stream
path is now exercised through shipped code, the host bridge is exercised
separately against a pty, and the two still meet only in a test. Closing that
properly means `_do_debug_unix` owning both ends of a pty pair it creates —
handing the slave path to the boot script and pumping the master to a localhost
port. That is a real feature, not a wiring tweak, and wants its own ticket.

## Criterion 1 met on PYBD_SF6 (2026-08-08, HEAD 12bb383, micropython 11828bf02e, micropython-lib 85ed324)

`mpremote debug hil` against a `dap_device` target reaches a breakpoint in
`target.py`, reads the frame back, and resumes to a second stop, with no address
of any kind in the config or on the command line. Recorded by
`tests/hil/test_hil_serial_dap.py`, results in `../20260808_hil_PYBD_SF6.md`.

**On PYBD_SF6, not rpi_pico_w.** "Multi-CDC" is a per-board claim and this is one
board's answer; the pico_w's own is untested and stays that way until it is
powered up. Criterion 2 is still open for the reason the bench note gives: a
negative probe has to come from a board with no second CDC, and there isn't one
here.

The activation gap is closed for real, not moved. Three things had to be true at
once, and each was a separate finding:

- **The device picks the channel, not the host.** `dap_stream="board"` is what
  `do_debug` sends; the host knows a tty node and the device knows a runtime
  object, and only the device can map one to the other. An earlier shape passed
  the host's path down and could not work by construction.
- **`pyb.USB_VCP(1)` constructing is not evidence the interface exists.** It
  answers from the build-time `MICROPY_HW_USB_CDC_NUM`. What boot actually
  enumerated is in `pyb.usb_mode()`, whose name carries the count, so that is
  what `_board_dap_stream()` reads. `isconnected()` is not usable as the test
  either: the host opens the interface only after reading the handshake this
  feeds, so it is False on every run that then succeeds.
- **Failing to get the requested stream must raise.** Falling back to TCP leaves
  the device reporting an endpoint the caller has no client for, because the
  caller is a bridge already waiting on the stream.

`caps["serial_dap"]` therefore reports which channel this session took. It is
`False` in a REPL probe on the same board, which is correct and is why it stays
out of `KNOWN_CAPABILITIES`: as a `requires` key it would fail every target that
named it, before the run that could satisfy it.

### The defect this exposed

Every DAP message over 1024 bytes desynchronised the link. Bisected by payload
size (512 bytes fine at ~10 kB/s, 1024 never answered), then measured at the raw
layer: `USB_VCP.write` returns 1024 for any request ≥ 2048, because
`pyb_usb_vcp_write` → `usbd_cdc_tx_flow` → `usbd_cdc_tx` writes what fits in
`MICROPY_HW_USB_CDC_TX_DATA_SIZE` and reports that count.

`StreamTransport.send` had a whole-buffer contract: it looped internally and
raised on timeout, which discarded the count of what had already gone out.
`public_api.py` drops the channel timeout to 1 ms once `initialize` is answered,
so the timeout expired mid-frame every time, and `_send_all` retried from offset
0 and resent the prefix. Not a visible error - a stream the peer can never parse
again.

`send` now has the socket contract: write once, return the count, raise EAGAIN
only when nothing went out. `_send_all` was already written to drive a frame out
from that count.

### Throughput, the 2026-08-07 section's open risk

16 KB `evaluate` response over the second CDC in 0.20 s, 81.7 kB/s, recorded by
the HIL run rather than asserted loosely. The byte-at-a-time `recv` is not the
bottleneck it was feared to be on hardware, so the chunked-read rewrite that
section calls for is not needed to make serial DAP usable. The desktop-pty
measurement it quotes (33.7 ms for 4095 bytes) does not transfer: a pty read
blocks where a CDC read returns short.
