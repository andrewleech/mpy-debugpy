# Q12: how the manifest says "this build has a second CDC interface"

Date: 2026-08-10
Top repo HEAD: f4814c4b2d54982eda8d0f044ba1ada7bbde68b0
micropython: 19410568d68fabe5d3fcf8594a4e30919205a7cd (mpy-debugpy)
micropython-lib: b829073c393f9ba1027fe8d526ea58c2c8eb7fe4 (mpy-debugpy)

## The question, and the premise that turned out to be wrong

Q12 asked how `firmware.toml` can advertise that a build can run DAP over an
interface of its own (STORY-6.1) without violating STORY-3.3's rule that the
manifest may never claim what a runtime probe would contradict. It recorded a
blocker: "`pyb.usb_mode()` reports the boot-time choice rather than the build's
maximum", and deferred the decision to STORY-3.2's republish.

The blocker is real about `usb_mode()` and false about the board. There are
three different questions here, and hardware measurement on a PYBD-SF6W
(session of 2026-08-08) showed they can each answer differently on the same
run:

| question | how you ask it | what changes it |
| --- | --- | --- |
| does the build have the interface | `pyb.USB_VCP(1)` constructs | recompiling |
| did this boot enumerate it | `pyb.usb_mode()` | `boot.py` |
| is a host holding it open | `USB_VCP.isconnected()` | plugging a cable |

`pyb.USB_VCP(id)` constructs iff `id < MICROPY_HW_USB_CDC_NUM`
(`ports/stm32/usb.c:696-708`), which is a compile-time constant. So the build
maximum *is* directly probeable, `usb_mode()` is simply the wrong instrument,
and the question is decidable now rather than at republish time.

## Decision

A boolean manifest capability, `second_cdc`, meaning the build has a second USB
CDC interface DAP could run over. Not a count.

- **Boolean, not a count.** `MICROPY_HW_USB_CDC_NUM` exists only in
  `ports/stm32` and `ports/mimxrt`. rp2 and esp32 express the same thing as
  TinyUSB's `CFG_TUD_CDC`, and ESP32_GENERIC has no USB device peripheral at
  all. A count would be a field three of the four current variants cannot fill
  in; the boolean is a question every port can answer.
- **Probed by the boot script, not by `debugpy.get_capabilities()`.** USB
  topology is not the debug server's concern, and `debugpy` is bound for
  upstream micropython-lib, where a board detail does not belong.
  `_probe_second_cdc()` in `mpy_launch_debugpy.py` constructs `pyb.USB_VCP(1)`
  and merges the result into the `caps` dict of the MPDBG-READY line. It
  `.copy()`s that dict first: with a session live, `get_capabilities()` returns
  the session's own dict, so adding a key to it would mutate session state.
- **Distinct from `serial_dap`.** `serial_dap` reports the channel one session
  took and is therefore not a firmware property; it never appears in the
  manifest. A board with a second CDC being debugged over TCP reports
  `second_cdc = true` and `serial_dap = false` in the same handshake. Collapsing
  them is exactly what Q12 ruled out.
- **False by default on every port but stm32.** That is the correct answer for
  all four current variants, but it is false by ignorance rather than by
  measurement: a port that gains a second CDC has to be taught to the probe
  before its manifest entry may claim it. Recorded in the probe's docstring.

## Why this needs no change to the capability guard

`capcheck.check_capabilities` only errors when a manifest claims exactly `True`
and the probe reports not-`True`. So a boolean key needs no guard change, and
the failure modes are asymmetric in the safe direction: a wrongly-`false`
manifest entry costs a user a variant they could have used, while a
wrongly-`true` one is a hard error on the first session.

## CI: `--report`, not `--expect`

The build-time evidence is `MICROPY_HW_USB_CDC_NUM >= 2`, which `--expect`
cannot express: `--expect MICROPY_HW_USB_CDC_NUM=1` is satisfied by a
single-interface build, whose macro is `1` - truthy, and meaning the opposite of
the capability. `verify_capabilities.py` gained `--report NAME=MACRO>=N`, which
derives rather than asserts:

- an undefined macro reports `false`, because for rp2/esp32/unix the undefined
  case is the real answer, whereas for `--expect` an undefined macro means the
  evidence is missing and nothing may be claimed;
- a macro defined to something that is not a plain integer is an error either
  way, because a value the script cannot read is not evidence of absence;
- reports are evaluated after the `--expect` failures are reported, so a build
  that fails an expectation says so rather than dying on a threshold beside it.

## Where the vocabulary now lives

Four hand-copies of the capability key set, none of which can import another:

| copy | role |
| --- | --- |
| `launcher/firmware.py` | `select --need` resolution |
| `launcher/gen_manifest.py` | fragment validation at assembly |
| `.github/scripts/write_fragment.py` | what a build job may emit |
| `mpremote/mpdebug_config.py` | what a target may name in `requires` |

`tests/test_gen_manifest.py` holds the first three to each other and
`tests/test_s5_2_mpdebug_config.py` holds the fourth, because otherwise a key
that one accepts and another rejects surfaces in a release job after every
artifact is already built.

`second_cdc` is in mpremote's `requires` vocabulary and `serial_dap` still is
not, for the reason above: a `requires` entry is checked against the handshake
of the run that just started, so requiring `serial_dap` would fail every target
before the run that could satisfy it, while `second_cdc` answers the same on
every run.

## Evidence

- `tests/test_q12_second_cdc.py` drives the shipped boot script under the real
  unix firmware with a `pyb` stub on `MICROPYPATH`. Each stub's `usb_mode()`
  deliberately contradicts its own interface count, so a probe reading
  `usb_mode` gets every case backwards. Mutating `_probe_second_cdc` to
  `return "xVCP" in (pyb.usb_mode() or "")` fails three of the five tests, and
  fails the two stub cases in opposite directions.
- `tests/hil/test_hil_serial_dap.py::test_hil_second_cdc_is_reported_as_a_build_property`
  is the positive on real hardware. It lives in that suite because it only runs
  when the board's second interface path was supplied, which is the one run
  where a `True` is guaranteed; the network suite's claimed-equals-probed check
  would otherwise be satisfied by two `False`s. `hil_facts` probes over the REPL
  independently of the handshake, so the two agreeing is two measurements.

## What is not done

All four `firmware.toml` entries carry `second_cdc = false`, including
`stm32-pybd-sf6-debug`. That entry's `source_commit` (f9d7c96b96) predates
`MICROPY_HW_USB_CDC_NUM (2)` reaching `boards/PYBD_SF6/mpconfigboard.h`, so
`false` is the honest value for the published artifact. It becomes `true` at
STORY-3.2's republish, from the CI `--report` rather than by hand. The
handshake from a locally-built PYBD firmware already reports `true`, which is
the asymmetry working as intended: the probe leads the manifest.

## Correction (2026-08-10): what a `true` here does not mean

The decision stands - `second_cdc` measures the build's maximum, and that is the
right question for a manifest, which describes a build and not a boot. What was
missing is the consequence, and it was being read the other way round: a `true`
means the build *could* enumerate a second interface, never that a board has one
ready. `ports/stm32/main.c:688-695` brings up a single VCP unless `boot.py` has
already called `pyb.usb_mode()`, so on a stock board every entry in the middle
row of the table above answers no while the top row answers yes. That is the
three-way distinction working exactly as described here; the error was elsewhere,
in treating the serial transport as the low-setup path on the strength of the top
row. See `20260810_single-uart-dap-framing.md` and D7.

One factual correction to the CI section, found while checking whether "no board
enumerates a second CDC by default" holds across the tree. It does, but not for
the reason given above: `MICROPY_HW_USB_CDC_NUM` is *read* only by
`ports/stm32/usb.c`. `ports/mimxrt/boards/PHYBOARD_RT1170/mpconfigboard.h`
defines it as `(2)` and nothing on that port consumes it - mimxrt takes
`CFG_TUD_CDC` from `shared/tinyusb/tusb_config.h`, which derives it from the
boolean `MICROPY_HW_USB_CDC`. So "exists only in `ports/stm32` and
`ports/mimxrt`" is true of where the macro appears and misleading about where it
means anything, and the `--report second_cdc=MICROPY_HW_USB_CDC_NUM>=2` rule
would report true for a mimxrt build enumerating one interface. Latent only: no
current variant is mimxrt. Recorded in `verify_capabilities.py`'s own docstring,
where someone adding a build job will meet it.
