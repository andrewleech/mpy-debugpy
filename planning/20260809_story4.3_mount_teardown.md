# STORY-4.3: what a mounted session's ending actually looks like

Date: 2026-08-09
HEAD: e43e149 (micropython 49502103e3, micropython-lib 84aaf65)

STORY-4.3's third criterion - "the mount is torn down on every exit path,
including exception and Ctrl-C" - turned out to be the hard half of the story,
and the two defects it exposed were both in code the criterion reaches rather
than in the new mount path. Recorded here because the reasoning is not
recoverable from the diffs, and because the second defect had been visible as
a symptom for some time under a wrong explanation.

## Teardown has two endings, and they are not the same claim

A mounted session ends in one of two states, and "teardown works" means
something different in each. Conflating them is what made the first version of
the end-to-end test assert something false.

**The client left first.** A DAP client that disconnects, or simply goes away,
releases the target: the device's own `process_pending_messages` finds the
channel gone, ends the session, and the program runs to completion untraced,
leaving the board at a raw-REPL prompt. Teardown then has a responsive device
to unmount, so the correct outcome is *silence* - no warning at all. A warning
here would be the ordinary path telling users to power cycle hardware that is
fine.

**The client is still attached.** The program is parked in `wait_for_continue`
waiting for a `continue` that will never come, and nothing on the device is
reading the port. An interrupt cannot reach a program that is not reading
stdin, so `_teardown_mount` can only time out. This is the one case where
"only a power cycle clears it" is the truth. What teardown must do is stay
bounded by its own timeout, exit zero (a signal ending a mounted session is a
normal end), and emit exactly one actionable line.

The original single test asserted `"power cycle" not in stderr` while the
client was still attached and the target still paused - precisely the case
where that warning is correct. It had also placed its device-reachability
check after the `try/finally`, so that half had never executed. The suite now
has one test per ending.

## Defect 1: the message pump raised into the debugged program

`process_pending_messages` restored the channel's blocking mode in a
`finally`, and the loop it guards is exactly what closes that channel: a DAP
`disconnect` request handled there runs the whole session teardown, so on the
way out of that request the socket is already gone and `settimeout` raises
`OSError: EBADF`. Every caller of that method is `_trace_function`, so the
exception landed in whichever line of the debugged program was being traced
and killed the program with a traceback naming an errno that belongs to the
debug channel, not to anything the program did.

This is deterministic, not a race: it fires for every session that ends the
ordinary way. It had been showing up as an intermittent-looking traceback and
was previously filed as a timing problem.

Downstream it was worse than cosmetic. The dead program's traceback reached
mpremote as the umount exec's stderr, so `_teardown_mount` raised
`TransportExecError` and told the user to power-cycle a board that was
demonstrably healthy - a following `exec` on the same port returned 0.

## Defect 2: teardown could not tell "refused" from "unreachable"

`TransportExecError` *proves the device answered*: it carries a status code and
error output, which only exist because the raw REPL took a command and
returned a result. Reporting it with the same "only a power cycle clears it"
text as a timeout inverts the advice for that branch. The two are now
separate, because they ask opposite things of the user - a device that
answered and refused the umount wants a reconnect and a manual umount, a
device that cannot be reached at all wants a power cycle.

The device's error output is also a multi-line traceback. Interpolated whole,
it made the first line of a one-line warning read `Traceback (most recent call
last):`, which tells a reader nothing. `_one_line` reduces it to its last
line, which is the part that names the error.

## Two hazards for anyone writing host-side tests against the unix firmware

Both cost real time here.

**Ctrl-D at the raw REPL ends the unix port's process.** `enter_raw_repl`
defaults to `soft_reset=True`, and a soft reset on the unix port is process
exit (`rc=0`), which hangs up the pty. A reachability check written with the
default therefore *destroys* the device it is checking, and the resulting
cascade - `read(1)` returning nothing, then `termios.tcgetattr` EIO, then
`TIOCMBIC` EIO out of `close()` - reads exactly like a session that left the
port broken. `mpremote resume` passes `soft_reset=False` for the same reason;
so must any in-process check.

A related non-issue, ruled out by measurement: closing the last pty *slave* fd
does not disturb the firmware holding the master. It stays alive, emits
nothing, and the slave path remains openable, because the devpts entry lives
as long as the master does. Holding a spare slave fd open for a session's
lifetime buys nothing.

**Leaked firmware processes perturb unrelated tests.** A test that fails
between spawning the unix firmware and reaping it leaves a process spinning at
roughly full CPU. Eleven of them accumulated during this work and were enough
to make a timing-sensitive test in another file fail. When a timing assertion
starts failing for no reason, check `pgrep -f build-standard/micropython`
before believing it.

## Residual flakiness, not chased

One run in four of `tests/test_s4_3_mount_attach.py` failed in mount setup
with `timeout waiting for first EOF reception` and no command output at all,
before any handshake. The verifier hit the same class of failure once as a
missing `MPDBG-READY` line. Both point at the 300 ms the pty helpers allow for
the interpreter to reach its REPL before mpremote talks to it - a value shared
with every other pty helper in the suite, so raising it is a suite-wide change
rather than a fix for this story. Recorded here so the next occurrence is
recognised rather than re-diagnosed.
